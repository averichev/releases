# Правила работы над Veruna Releases

Не поддакивай. Критикуй решения, если они увеличивают стоимость поддержки или противоречат общей логике приложения. Выбирай простые изменения с понятными границами. Задавай уточняющие вопросы, когда ответ меняет архитектуру или пользовательское поведение; рутинные решения принимай самостоятельно.

## Назначение и границы

- Это независимая платформа распространения разных программных продуктов. Не зашивай имена, версии, платформы или протоколы конкретного продукта в основу сервиса.
- Один Rust package, один исполняемый файл, SQLite и отдельный каталог дистрибутивов. Не вводи workspace, микросервисы, DI-контейнер, универсальный CRUD или repository framework без реальной необходимости.
- Этап 1 не реализует авторизацию, приложения, релизы, каналы, загрузку файлов, манифесты или статистику. Не добавляй фиктивные данные, модели с предположительными полями и функции-заглушки, возвращающие успех.
- Будущие сущности: Application, Release, Artifact, Channel, User, ApiToken, DownloadEvent. Добавляй их вместе с конкретным use case и инвариантами.

## Backend

- `domain/`: доменные модули, инварианты и типы; без Axum, SQLx и файловой системы.
- `services/`: сценарии и координация; без HTTP DTO и кодов ответа.
- `repositories/`: конкретный SQL и преобразование данных. Не вводи trait для каждого репозитория автоматически.
- `infrastructure/`: SQLite/pool, logging, сигналы и файловое хранилище. Доступ к дистрибутивам — только через `ArtifactStorage`; не обходи этот интерфейс из HTTP или сервисов.
- `http/`: маршруты, запросы/ответы, централизованное отображение ошибок, middleware и встроенные assets. SQL в обработчиках запрещён.
- `main.rs` и `initialize` — composition root. Подключение новых адаптеров и зависимостей выполняется там.
- HTTP DTO отделяй от доменных сущностей. Не раскрывай SQL, пути на диске, токены, внутренние ошибки и тела запросов в публичных ответах или логах. Внутренние причины ошибок логируй один раз на границе.
- Публичное API — `/api/v1`; административное — `/api/v1/admin`. Пока нет реальной авторизации, административная граница всегда закрыта. Нельзя снимать gate просто ради работающего endpoint.
- Внедряя авторизацию, сначала добавь middleware и тесты неавторизованных/запрещённых запросов; затем подключай административные сценарии. Видимость React-страниц не является защитой API.
- Не добавляй блокирующий I/O в async-обработчики. Проверяй входные размеры и используйте потоковую передачу, когда появятся дистрибутивы.
- Не используй `unwrap`/`expect` для рабочих ошибок; они допустимы в тестах и явных проверках сборки. Не подавляй lint, чтобы скрыть неиспользуемые заготовки.

## Данные и миграции

- Настройки SQLite: foreign keys на каждом соединении, WAL, bounded pool и busy timeout. БД и артефакты хранятся на локальном диске отдельно от встроенных ресурсов.
- Миграции — только новые нумерованные `.sql` в `migrations/`. Не изменяй уже применённые миграции; SQLx проверяет checksum.
- Для реальных сущностей задавай ограничения, индексы и транзакции одновременно с бизнес-правилами. Не создавай таблицы «на будущее».
- Не считай транзакцию БД атомарной с файловой системой. При внедрении загрузок спроектируй временные файлы, атомарное перемещение и восстановление после сбоя.
- Не принимай пользовательский путь как путь на диске. Будущие операции хранилища должны использовать проверенные непрозрачные ключи и предотвращать обход каталога, включая symlink.

## Frontend

- React + TypeScript strict + Vite + Ant Design. Используй существующие компоненты и токены темы. Не добавляй вторую UI-библиотеку или глобальный state manager без необходимости.
- Маршруты панели — `/admin/...`, ссылки — React Router. Прямое открытие и перезагрузка вложенной страницы должны работать.
- Реальные данные получай через API. Различай загрузку, ошибку и успешный ответ. Не показывай «всё работает» до ответа сервера.
- Не добавляй неработающие кнопки создания, фальшивые записи, статистику и выдуманные пользовательские профили.
- Asset URL — от корня домена. Не используй CDN, внешние шрифты или сторонние runtime-ресурсы для базовой панели.
- Не превращай 404 API или отсутствующего `.js`/`.css` в `200 index.html`. SPA fallback ограничен маршрутами документов панели.

## Проверка изменений

Из корня проекта:

```sh
sh scripts/check.sh
sh scripts/build.sh
python3 scripts/smoke.py
```

- Для первого запуска Cargo сначала собери UI. Не коммить `target`, `node_modules`, `dist`, локальную конфигурацию, БД и дистрибутивы. Оба lock-файла сохраняй.
- Для небольших правок достаточно относящихся к ним проверок; перед завершением этапа обязательны полная сборка, тесты, Clippy без предупреждений, проверка типов и smoke.
- Добавляй тесты поведения и границ, особенно HTTP, конфигурации и сохранности данных. Не размножай проверки, которые повторяют реализацию.
- Обновляй README и архитектурные решения при изменении конфигурации, маршрутов, сборки или границ модулей.
- Перед сдачей интерфейса проверь его в браузере, включая вложенный маршрут и узкий экран.
