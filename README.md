# Релизы

Самостоятельная платформа распространения ПО. Этап 6: публичные страницы и скачивания, Range/докачка, direct и Nginx X-Accel-Redirect, рабочие манифесты и динамический Tauri Updater v2.

В интерфейсе используется логотип «Выход»: монограмма «Р» на лаймовой подложке и векторная надпись «Релизы». Общий компонент `frontend/src/components/Brand.tsx` используется в панели, на входе/активации и публичных страницах. Мастера и набор размеров находятся в [assets/brand](assets/brand/README.md). Технические имена бинарника `veruna-releases`, конфигурации и HTTP-протокола сохранены для совместимости.

Реализованы каталог приложений с поиском, фильтрами, иконками, настройками и архивом, администраторы и операторы, приглашения, восстановление и смена пароля, блокировка и отзыв сессий. Реализованы черновики релизов, SemVer, потоковая загрузка с назначением installer/updater и `.sig`, защищённое скачивание, удаление черновиков и проверка SHA-256. Опубликованный релиз можно дополнить новыми неизменяемыми артефактами той же версии; существующие файлы и первая дата публикации сохраняются. Порядок работы и правила выбора установщика: [управление релизами](docs/release-management.md). Публикация, история и публичные манифесты реализованы. Публичное распространение и Tauri endpoint реализованы. Статистика, OAuth/OIDC, email и CI/CD API-токены не реализованы. Публичной регистрации нет. `/api/v1/health` доступен без авторизации.

## Требования

- Rust 1.91+ с Cargo, rustfmt и Clippy; системный C toolchain для сборки SQLite.
- Node.js 20.x (от 20.19), 22.x (от 22.12) или 24+ и npm; для нового окружения используйте поддерживаемую LTS-ветку Node.js, совместимую с `frontend/package.json`.
- Python 3.11+ — для расчёта версии релиза и smoke-тестов; без сторонних библиотек.

Версии зависимостей фиксируются `Cargo.lock` и `frontend/package-lock.json`. SQLx 0.8.6 выбран для совместимости с Rust 1.91; переход на 0.9 требует отдельного обновления Rust. SQLite собирается вместе с SQLx: системный сервер БД и SQLx CLI не нужны.

## Быстрый запуск

Все команды ниже выполняются из корня проекта:

```sh
npm --prefix frontend ci
npm --prefix frontend run build
cargo run --locked -- admin bootstrap
cargo run --locked
```

Bootstrap запрашивает логин и пароль с подтверждением; пароль не отображается. Логин: 3–64 ASCII-символа `a-z`, `0-9`, `.`, `_`, `-`, без различия регистра. Пароль: 12–128 Unicode-символов (до 512 байт). Администратор создаётся активным. Если в БД уже есть администратор, команда ничего не меняет и не читает пароль. Команда не запускает HTTP-сервер и не требует доступа к каталогу дистрибутивов.

При обычном локальном запуске приложение само открывает `/admin` в браузере по умолчанию. Без сессии появится страница входа; используйте созданную учётную запись. По умолчанию сервер занимает `127.0.0.1:8080`. Если порт занят, ОС выделяет свободный порт; фактический адрес выводится в консоль и используется для браузера, авторизации и ссылок скачивания. Проверить сервер (подставьте выбранный порт, если 8080 был занят):

```sh
curl --fail http://127.0.0.1:8080/api/v1/health
```

Ответ `200 application/json` после успешного `SELECT 1`:

```json
{"status":"ok","service":"veruna-releases","version":"0.1.0"}
```

Если база недоступна — `503` и `{"error":{"code":"database_unavailable","message":"Service is not ready"}}`. Это проверка готовности HTTP/БД, а не полный аудит диска или внешних зависимостей.

При первом запуске автоматически создаются `data/veruna.sqlite`, родительские каталоги и `data/artifacts`, а также отдельный каталог `data/icons`. Миграции применяются до открытия HTTP-порта. Ошибки конфигурации, миграций, файловой системы или привязки порта завершают процесс с ненулевым кодом. Ошибка открытия браузера оставляет сервер работающим: адрес можно открыть вручную. Команды `admin bootstrap` и `admin reset-password` браузер не открывают.

## Разработка

Сначала один раз выполните сборку фронтенда из быстрого запуска. Затем два терминала:

```sh
# Терминал 1: backend; после изменений Rust перезапустите команду.
AUTH__PUBLIC_ORIGIN=http://127.0.0.1:5173 cargo run --locked
```

```sh
# Терминал 2: Vite с HMR.
npm --prefix frontend run dev
```

Для разработки интерфейса открывайте [Vite](http://127.0.0.1:5173). Он проксирует `/api` на `http://127.0.0.1:8080`, поэтому CORS не требуется. При другом адресе backend:

```sh
DEV_API_TARGET=http://127.0.0.1:9090 npm --prefix frontend run dev
```

Порт Rust продолжает обслуживать **последнюю встроенную сборку**. Чтобы обновить её, выполните `npm --prefix frontend run build` и перезапустите `cargo run --locked`. Ресурсы встроены и в debug-, и в release-бинарник. `build.rs` отслеживает `frontend/dist` и миграции; без предварительно собранного фронтенда Cargo завершится с инструкцией по сборке. Cargo не запускает npm и не устанавливает JS-зависимости неявно.

## Конфигурация

Приоритет: встроенные значения → `veruna.toml` → переменные `SERVER__…`, `DATABASE__…`, `STORAGE__…`, `LOGGING__…`, `AUTH__…`, `DOWNLOAD__…`. Конфигурационный файл необязателен; скопируйте `veruna.example.toml` в `veruna.toml`, если нужна локальная настройка. `.env` автоматически не загружается.

Можно выбрать другой TOML-файл:

```sh
CONFIG=/etc/veruna/releases.toml ./target/release/veruna-releases
```

Явно указанный файл обязан существовать. Неизвестные поля и опечатки в этих переменных, неверные типы и недопустимые значения приводят к ошибке запуска. Относительные пути всегда отсчитываются от **рабочего каталога процесса**, а не от расположения TOML или бинарника. Для production используйте абсолютные пути.

| TOML | Переменная | По умолчанию |
| --- | --- | --- |
| `server.bind` | `SERVER__BIND` | `127.0.0.1:8080` |
| `server.auto_port` | `SERVER__AUTO_PORT` | `true` |
| `server.open_browser` | `SERVER__OPEN_BROWSER` | `true` |
| `server.shutdown_timeout_seconds` | `SERVER__SHUTDOWN_TIMEOUT_SECONDS` | `15` |
| `database.path` | `DATABASE__PATH` | `data/veruna.sqlite` |
| `database.max_connections` | `DATABASE__MAX_CONNECTIONS` | `4` |
| `database.busy_timeout_seconds` | `DATABASE__BUSY_TIMEOUT_SECONDS` | `5` |
| `storage.directory` | `STORAGE__DIRECTORY` | `data/artifacts` |
| `storage.icons_directory` | `STORAGE__ICONS_DIRECTORY` | `data/icons` |
| `storage.temporary_directory` | `STORAGE__TEMPORARY_DIRECTORY` | `<storage.directory>/.tmp` |
| `storage.max_file_bytes` | `STORAGE__MAX_FILE_BYTES` | `2147483648` (2 GiB) |
| `storage.max_request_bytes` | `STORAGE__MAX_REQUEST_BYTES` | `2148532224` |
| `storage.upload_idle_seconds` | `STORAGE__UPLOAD_IDLE_SECONDS` | `120` |
| `auth.public_origin` | `AUTH__PUBLIC_ORIGIN` | автоматически из запроса |
| `auth.session_ttl_seconds` | `AUTH__SESSION_TTL_SECONDS` | `43200` (12 часов) |
| `auth.invitation_ttl_seconds` | `AUTH__INVITATION_TTL_SECONDS` | `86400` (24 часа) |
| `download.public_base_url` | `DOWNLOAD__PUBLIC_BASE_URL` | автоматически из запроса |
| `download.delivery_mode` | `DOWNLOAD__DELIVERY_MODE` | `direct` |
| `download.max_concurrent_downloads` | `DOWNLOAD__MAX_CONCURRENT_DOWNLOADS` | `64` |
| `logging.filter` | `LOGGING__FILTER` | `info,tower_http=info` |

`server.bind` — IP и порт, например `127.0.0.1:8080`, `0.0.0.0:8080` или `[::1]:8080`. Размер пула — 1–32, таймауты — 1–300 секунд. Логи JSON выводятся в stdout; HTTP-логи содержат метод, шаблон маршрута, статус и длительность; адреса, query string, тела и заголовки с секретами не логируются. Фильтр настраивается через TOML или `LOGGING__FILTER`; `RUST_LOG` не используется.

Автовыбор порта работает только для loopback IP, когда `auth.public_origin` и `download.public_base_url` не заданы либо равны `http://<server.bind>`. При занятом порте listener сразу привязывается к свободному порту без отдельной проверки с освобождением сокета; явно заданные локальные origin обновляются до создания HTTP-состояния. `server.auto_port = false` оставляет порт фиксированным. Внешние origin (включая Vite), привязка к `0.0.0.0`/`[::]` и HTTPS сохраняют настроенный порт, чтобы не нарушить proxy и постоянные URL.

Браузер открывается только при `server.open_browser = true`, loopback-привязке и автоматическом origin либо его совпадении с фактическим HTTP-адресом. Используются системные `open` на macOS, `rundll32.exe` на Windows и `xdg-open` на Linux. Для запуска без рабочего стола задайте `server.open_browser = false` или `SERVER__OPEN_BROWSER=false`. При отдельном Vite origin браузер автоматически не открывается.

## Production

### Релиз для Linux, Windows и macOS

На macOS с Xcode Command Line Tools команда собирает UI один раз, затем три release-бинарника со встроенными assets и миграциями, без архивов:

```sh
make release
```

| Платформа | Rust target | Файл (версия из Git) |
| --- | --- | --- |
| Linux x86_64 | `x86_64-unknown-linux-musl` | `veruna-releases-<version>-linux-x86_64` |
| Windows x86_64 | `x86_64-pc-windows-gnu` | `veruna-releases-<version>-windows-x86_64.exe` |
| macOS Apple Silicon | `aarch64-apple-darwin` | `veruna-releases-<version>-macos-aarch64.tool` |

Однократная подготовка, помимо Python 3.11+, Node.js/npm и Rust через rustup:

```sh
xcode-select --install # если Command Line Tools ещё не установлены
brew install python zig mingw-w64
cargo install --locked cargo-zigbuild
rustup target add --toolchain stable aarch64-apple-darwin x86_64-unknown-linux-musl x86_64-pc-windows-gnu
```

Сборка явно использует rustup toolchain `stable`, чтобы Cargo, rustc и установленные target-библиотеки не смешивались с Rust из Homebrew. Для другой установленной версии: `RELEASE_TOOLCHAIN=1.91.1 make release`; targets должны быть установлены в выбранном toolchain. Скрипт проверяет зависимости до сборки и не устанавливает их автоматически. Linux собирается через [cargo-zigbuild](https://github.com/rust-cross/cargo-zigbuild), Windows — через MinGW, macOS — системным Apple toolchain.

Для линковки Zig скрипт поднимает мягкий лимит открытых файлов до 8192, если текущий ниже, сохраняя жёсткий лимит и настройки родительского терминала. Это предотвращает `ProcessFdQuotaExceeded` при сборке Linux musl со стандартным лимитом macOS в 256 файлов. Если жёсткий лимит не позволяет повышение, скрипт завершится до сборки с диагностикой.

Версия рассчитывается по **последнему достижимому стабильному Git-тегу `vX.Y.Z`** и коммитам после него. Выбирается самое большое повышение из Conventional Commits:

| Изменение | Повышение |
| --- | --- |
| `fix`, `perf`, `revert` | patch: `0.2.0` → `0.2.1` |
| `feat` | minor: `0.2.1` → `0.3.0` |
| `!`, `BREAKING CHANGE:` или `BREAKING-CHANGE:` | major после `1.0`; до `1.0` — minor |
| Только `docs`, `test`, `chore`, `build`, `ci`, `style`, `refactor` без breaking change | новый релиз не нужен |

Если тегов ещё нет, базовая версия берётся из `Cargo.toml`, учитываются все коммиты. С текущей историей база `0.1.0` даёт первый автоматический релиз `0.2.0`. Если `HEAD` уже имеет стабильный тег, собирается его версия без повышения. Prerelease-теги не используются как база. Нужна полная локальная история Git с актуальными тегами; скрипт не делает fetch автоматически. Для shallow clone сначала выполните `git fetch --unshallow --tags`.

Посмотреть расчёт без сборки, изменения файлов и тегов можно даже с незакоммиченными правками:

```sh
make release-plan
```

Для самого выпуска рабочее дерево должно быть чистым: сначала зафиксируйте изменения. Расчётная версия встраивается в бинарник через build-time `RELEASE_VERSION` и совпадает с `/api/v1/health`, логом запуска, именами файлов и каталогом. `Cargo.toml`, `Cargo.lock` и frontend package/lock не переписываются сборкой; обычный `cargo build` использует базовую Cargo-версию.

После успешной сборки **всех трёх платформ** готовый каталог атомарно переносится в `dist/releases/<version>/`, затем создаётся локальный Git-тег `v<version>` на исходном коммите. Новых коммитов и отправки в GitHub нет. Результат, например:

```text
dist/releases/0.2.0/
  veruna-releases-0.2.0-linux-x86_64
  veruna-releases-0.2.0-windows-x86_64.exe
  veruna-releases-0.2.0-macos-aarch64.tool
  release.json
  SHA256SUMS
```

`release.json` содержит версию, SHA коммита и предыдущий тег; `SHA256SUMS` проверяет три бинарника и эти метаданные. Проверка: `cd dist/releases/0.2.0 && shasum -a 256 -c SHA256SUMS`. Повторный `make release` на том же коммите проверяет суммы и использует готовый результат; старые каталоги, включая прежний `0.1.0`, не перезаписываются и не удаляются. При повреждённом или чужом каталоге команда останавливается. Если каталог отсутствует, тег можно пересобрать. Если после сохранения файлов не удалось создать тег, повторный запуск завершит создание тега без пересборки.

Ошибка сборки не создаёт итоговый каталог или тег и не расходует номер версии. Параллельный выпуск в одном checkout запрещён блокировкой; изменение Git или файлов во время сборки отменяет публикацию результата. Каталоги `dist/` и `target/` исключены из Git. Сборка не публикует файлы и не подписывает бинарники. Проверка запуска выполняется отдельно; на Apple Silicon: `python3 scripts/smoke.py dist/releases/0.2.0/veruna-releases-0.2.0-macos-aarch64.tool 0.2.0` (последний аргумент дополнительно проверяет встроенную версию).

Для запуска по клику выберите файл своей ОС и архитектуры: `.exe` в Windows, `macos-aarch64.tool` на Mac с Apple Silicon, `linux-x86_64` на Linux x86_64. На macOS `.tool` открывается через Terminal, который запускает бинарник; это тот же Mach-O файл, без скрипта-обёртки. Суффикс нужен Finder, чтобы точки в версии не воспринимались как неизвестное расширение документа. После успешного старта откроется браузер. Unix-бинарники сохраняют право исполнения при сборке; если способ передачи снял его, выполните `chmod +x <файл>`. На Linux запуск по клику также зависит от настроек файлового менеджера; нужен рабочий стол с `xdg-open`. Бинарники не подписаны: системные правила запуска загруженных приложений продолжают действовать. Файл Linux нельзя запускать на macOS — это вызывает `exec format error`.

### Запуск через «Мой хост»

Для порта `3001` в форме приложения задайте:

```text
SERVER__BIND=127.0.0.1:3001
SERVER__AUTO_PORT=false
SERVER__OPEN_BROWSER=false
```

Порт в форме «Мой хост» должен совпадать с `SERVER__BIND`. После привязки HTTPS-сайта домен определяется автоматически: «Мой хост» уже передаёт `Host` и `X-Forwarded-Proto` через локальный nginx. `AUTH__PUBLIC_ORIGIN` и `DOWNLOAD__PUBLIC_BASE_URL` задавать не требуется. В существующем TOML удалите эти два значения или оставьте пустыми, чтобы включить автоматический режим.

Имена переменных изменены: удалите `VERUNA__` перед разделом (`VERUNA__SERVER__BIND` → `SERVER__BIND`); `VERUNA_CONFIG` заменён на `CONFIG`, `VERUNA_DEV_API_TARGET` — на `DEV_API_TARGET`. Старые серверные имена вызывают понятную ошибку запуска, чтобы порт или пути не сбросились незаметно. TOML-ключи не переименованы.

### Сборка для текущей системы

```sh
sh scripts/build.sh
python3 scripts/smoke.py
```

Результат — `target/release/veruna-releases`: скрипт явно задаёт `--target-dir target`, в том числе при пользовательских глобальных настройках Cargo. Перенесите на совместимую ОС и архитектуру **только бинарник**, при необходимости добавив TOML. Для запуска не нужны Node.js, `frontend/dist`, исходники или каталог миграций. Внешние данные — SQLite, каталог дистрибутивов и каталог иконок — остаются на диске.

```sh
SERVER__BIND=127.0.0.1:8080 \
SERVER__AUTO_PORT=false \
SERVER__OPEN_BROWSER=false \
DATABASE__PATH=/var/lib/veruna-releases/database/releases.sqlite \
STORAGE__DIRECTORY=/var/lib/veruna-releases/artifacts \
STORAGE__ICONS_DIRECTORY=/var/lib/veruna-releases/icons \
./veruna-releases
```

Процесс должен иметь права создавать каталоги и файлы в указанных местах. SQLite работает в `WAL` с `foreign_keys=ON` для каждого соединения, `synchronous=FULL` и ожиданием блокировки. Используйте локальный диск; рядом с БД могут появляться `-wal` и `-shm`. Каталог дистрибутивов не публикуется как статический каталог. Не размещайте данные в `frontend/public` или `frontend/dist`.

Предполагаемая установка — `https://apps.veruna.systems` в корне домена. TLS завершается на reverse proxy, который передаёт **все** пути Rust-серверу. Например, Caddy:

```caddyfile
apps.veruna.systems {
    reverse_proxy 127.0.0.1:8080
}
```

Отдельный веб-сервер для assets не требуется. Префикс вроде `/releases/` сейчас не поддерживается. `/admin/...` отдаёт HTML оболочки; React проверяет сессию до отображения панели. Данные и действия защищены backend middleware. Операторы не могут управлять пользователями даже прямым API-запросом.

`Ctrl+C`/SIGINT и SIGTERM на Unix останавливают приём соединений, дают текущим запросам до `shutdown_timeout_seconds` на завершение, затем закрывают пул БД с таким же отдельным пределом. Превышение лимита завершается ошибкой. Таймаут остановки service manager должен превышать сумму двух лимитов; при значении 15 секунд задайте не менее 35 секунд.

## Проверки

```sh
sh scripts/check.sh
sh scripts/build.sh
python3 scripts/smoke.py
```

Дополнительная проверка Linux за настоящим локальным nginx с TLS: `python3 scripts/smoke_origin.py`. Требует собранного Linux x86_64-бинарника (`make release`), Docker и OpenSSL; проверяет порт 3001, два автоматических домена, Secure-cookie, CSRF, приглашения и Tauri URL без настроек публичных адресов. Можно передать путь к бинарнику первым аргументом.

`check.sh` проверяет расчёт версий/теги/сохранность выпусков во временных Git-репозиториях, устанавливает зависимости по lock-файлу, проверяет TypeScript, собирает UI, запускает Vitest, `cargo fmt --check`, Rust-тесты и `cargo clippy --all-targets -- -D warnings`.

Тесты проверяют приоритет и ошибки конфигурации, реальные файловые пути, настройки соединений SQLite, повторное применение миграций, схему пользователей, health и его отказ, блокировку административного API, JSON-ошибки, SPA-маршруты, статические ресурсы и HEAD. Тесты авторизации покрывают bootstrap (включая настоящий CLI), вход и лимиты, роли, CSRF, приглашения и восстановление, истечение, смену пароля, отзыв сессий и конкурентную защиту последнего администратора. Фронтенд проверяет загрузку сессии, вход, вложенные страницы, запрет управления для оператора, истечение сессии, ошибки и запросы с CSRF. Smoke-тест запускает production-бинарник из временного пустого каталога, загружает HTML/JS/CSS, проверяет БД и завершает процесс SIGTERM.

Архитектура и развитие: [docs/architecture.md](docs/architecture.md). Правила внесения изменений: [AGENTS.md](AGENTS.md).

## Пользователи и сессии

В разделе **Пользователи** администратор добавляет учётную запись с паролем либо создаёт приглашение с ролью. Предпочтительный способ — приглашение: пользователь сам задаёт пароль. Ссылка показывается один раз, email не отправляется. Она содержит токен в URL fragment (`#token=…`), который не передаётся HTTP-серверу и в Referer. Передайте ссылку лично. Повторная выдача отменяет старую; после использования или истечения ссылка недействительна.

Dropdown пользователя позволяет изменить роль, заблокировать/разблокировать, повторить приглашение, создать ссылку восстановления пароля и отозвать все сессии. Отключение приглашённого отзываeт приглашение; после разблокировки учётная запись возвращается в `invited`, нужно выдать новую ссылку. Смена роли также завершает сессии. Последнего активного администратора нельзя отключить или понизить; сначала создайте или активируйте другого администратора.

Забытый пароль восстанавливается администратором через **Восстановить пароль** в этом же меню. Ссылка одноразовая с тем же сроком, что приглашение; при установке нового пароля все сессии отзываются. Если пароль потерян у единственного администратора, владелец сервера запускает `veruna-releases admin reset-password` с той же конфигурацией БД. Команда запрашивает логин активного администратора и показывает одноразовый путь в консоли (откройте его на домене панели; при явном `auth.public_origin` выводится абсолютная ссылка); HTTP-сервер для выдачи не нужен. Для pipe доступен `admin reset-password --stdin` (одна строка — логин). Предыдущая ссылка отменяется, пароль и сессии меняются только при использовании новой ссылки. Ссылку нельзя сохранять в общедоступных логах. Bootstrap существующего администратора не сбрасывает. Публичного сброса пароля нет.

В профиле доступны смена собственного пароля с проверкой текущего и выход. После смены пароля необходимо войти заново на всех устройствах. Сессии сохраняются после перезагрузки страницы и перезапуска сервера, имеют абсолютный срок (без продления на запросах) и максимум 20 сессий на пользователя. В БД находятся только SHA-256-хеши 256-битных случайных идентификаторов и одноразовых токенов. Пароли хешируются Argon2id (19 MiB, 2 прохода, parallelism 1), в отдельном блокирующем пуле с максимум 4 одновременными операциями.

`auth.session_ttl_seconds`: 60–2592000; `auth.invitation_ttl_seconds`: 60–604800. `auth.public_origin` и `download.public_base_url` по умолчанию пусты: origin панели, приглашения, манифесты и Tauri используют домен текущего запроса. Необязательное явное значение задаёт фиксированный HTTPS origin без пути и завершающего `/`, например для отдельного домена скачиваний. HTTP разрешён только на loopback для разработки; production требует HTTPS. Cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age`; для HTTPS — `Secure` и имя `__Host-veruna_session` без Domain. Для HTTP разработки используется `veruna_session`.

Изменяющие запросы требуют совпадающего `Origin` и `X-Veruna-Request: 1`; аутентифицированные — также `X-CSRF-Token` из login/me. CSRF-токен живёт только в памяти UI, cookie недоступна JavaScript. CORS разрешён только для GET/HEAD публичного манифеста, каталога/истории/иконки и Tauri updater: любой Origin без credentials, подробнее в [публичном распространении](docs/public-distribution.md#cors). Вход ограничен пятью неудачными/выполняющимися попытками на нормализованный логин за 5 минут и общим пределом 100 за 5 минут. Успешные попытки освобождают лимит. Лимиты сохраняются в SQLite при перезапуске. Общий лимит консервативен для небольшой команды; при массовой атаке вход может временно ограничиваться для всех.

Для автоматизированного bootstrap доступен `veruna-releases admin bootstrap --stdin`: две строки UTF-8 — логин и пароль, каждая с переводом строки. Передавайте их через pipe из менеджера секретов; не помещайте пароль в аргументы, shell history или environment. Интерактивный пароль подтверждается, stdin-вариант требует явного флага и не принимает терминал.

### Reverse proxy

В автоматическом режиме домен берётся из проверенного `Host`, а HTTPS — из единственного `X-Forwarded-Proto`, только если TCP-соединение пришло с loopback IP. `Forwarded` и `X-Forwarded-Host` игнорируются. Публичный домен без подтверждённого HTTPS отклоняется; прямой HTTP разрешён только для loopback-адресов. Origin/custom-header/CSRF-проверки сохраняются. Backend слушает loopback и должен быть доступен только reverse proxy; proxy обязан перезаписывать `Host` и `X-Forwarded-Proto`. При proxy на другой машине задайте фиксированные URL в TOML. Пример Nginx внутри HTTPS server с настроенными сертификатами:

```nginx
# Внутри HTTPS server: 2 GiB на файл + 1 MiB на multipart.
client_max_body_size 2049m;
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_request_buffering off;
    proxy_read_timeout 180s;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header Forwarded "";
}
```

Не переписывайте браузерный `Origin` на стороне proxy. Включите перенаправление HTTP → HTTPS и защиту TLS/HSTS на reverse proxy. В автоматическом режиме дополнительные переменные с доменом не нужны. Если задан явный `auth.public_origin`, он должен совпадать с внешним адресом. Для Vite укажите `http://127.0.0.1:5173` в конфигурации backend.

Лимит в форме загрузки приходит от backend и не учитывает ограничения внешних прокси. Если файл меньше указанного размера, но загрузка получает HTTP 413, проверьте `client_max_body_size` в действующем `server`/`location` именно этого домена и лимиты других прокси перед ним. Nginx может отклонить запрос до backend и вернуть HTML; панель определяет такую ошибку по HTTP-статусу. После изменения конфигурации проверьте `nginx -t` и перезагрузите Nginx. Полный пример: [deploy/nginx/veruna.conf](deploy/nginx/veruna.conf).

### HTTP API этапа 2

| Метод и путь | Доступ / данные |
| --- | --- |
| `POST /api/v1/auth/login` | `{username,password}` → cookie, `{user,csrf_token}` |
| `GET /api/v1/auth/me` | сессия → `{user,csrf_token}` |
| `POST /api/v1/auth/logout` | сессия + CSRF → 204, отзыв текущей сессии |
| `POST /api/v1/auth/change-password` | сессия + CSRF, `{current_password,new_password}` → 204, отзыв всех сессий |
| `POST /api/v1/auth/token/check` | `{token}` → `{username,purpose}`; без сессии |
| `POST /api/v1/auth/activate` | `{token,password}` → 204; приглашение или восстановление |
| `GET /api/v1/admin/users` | admin → список безопасных DTO |
| `POST /api/v1/admin/users` | admin, `{username,role,password}` → активная учётная запись, 201 |
| `POST /api/v1/admin/users/invitations` | admin, `{username,role}` → `{activation_url,expires_at}`, 201 |
| `PATCH /api/v1/admin/users/{id}/role` | admin, `{role}` → 204 |
| `PATCH /api/v1/admin/users/{id}/status` | admin, `{status: active или disabled}` → 204 |
| `POST /api/v1/admin/users/{id}/invitation` | admin → новая ссылка для invited |
| `POST /api/v1/admin/users/{id}/password-reset` | admin → ссылка восстановления для active |
| `POST /api/v1/admin/users/{id}/revoke-sessions` | admin → 204 |

Все административные изменения требуют CSRF. Время в DTO — Unix seconds UTC. Ошибки: `400 invalid_request/invalid_token`, `401 unauthorized/invalid_credentials`, `403 forbidden`, `404 not_found`, `409 user_exists/last_active_admin`, `429 rate_limited`, `500 internal_error`, в envelope `{"error":{"code":"…","message":"…"}}`. Для авторизации и пользователей некорректный JSON и тела свыше 8 KiB дают безопасную ошибку 400. Каталог использует отдельные лимиты, описанные в [API каталога](docs/admin-api.md). Login не принимает поля роли или статуса. Изменение роли/статуса и отзыв собственных сессий требуют повторного входа.


## Каталог приложений (этап 3)

В разделе **Приложения** доступны карточки и таблица, поиск по названию/slug, фильтры статуса и публичности, сортировка и страницы результатов. По умолчанию показаны активные приложения. Условия поиска сохраняются в URL. Оператор может просматривать каталог, подробную информацию и иконки; создание, настройки, иконки, архивация и восстановление доступны только администратору. Backend проверяет права независимо от интерфейса.

При создании задаются название, постоянный slug, описание, иконка и публичность. Кириллица транслитерируется в предлагаемом slug; его можно изменить до сохранения. Новый продукт приватный и активный. Slug (1–64 символа `a-z`, `0-9`, дефис внутри) уникален, включая архив, и неизменяем. Служебные имена запрещены. Для будущих внутренних связей используется UUID. База не заполняется демонстрационными продуктами.

Страница `/admin/applications/:id` содержит обзор, список черновиков релизов и настройки (`/settings`). Прямое открытие и перезагрузка работают через встроенный HTTP-сервер. Название — до 120 Unicode-символов, описание — до 2000. Архив сохраняет UUID, slug и публичность; повторная архивация безопасна, восстановление возвращает продукт в активный каталог. Физического удаления нет. Версии и файлы доступны в защищённой панели; опубликованные версии публичных активных приложений доступны на страницах загрузки и в манифестах.

Иконки: PNG, JPEG, WebP, максимум 2 МиБ и 1024×1024. Сервер полностью декодирует содержимое и сохраняет нормализованный PNG без исходного имени и метаданных. SVG не принимается. Иконки хранятся в `storage.icons_directory`, отдельно от дистрибутивов: каталоги не должны совпадать или быть вложенными друг в друга, включая symlink-алиасы. Административная выдача требует сессию и использует `no-store`; на этапе 6 добавлена отдельная публичная выдача иконки active/public приложения через IconStorage. Без пользовательской иконки показывается стандартная.

Файловая система и SQLite не образуют одну транзакцию: файл сохраняется атомарным переименованием до записи ссылки в БД. При запуске до открытия порта удаляются временные и неиспользуемые файлы иконок, включая остатки неудачных загрузок. Заменённые и удалённые иконки занимают диск до следующего запуска — это также позволяет завершиться чтениям уже открытых изображений. Один экземпляр сервера управляет этими каталогами. Резервная копия должна включать БД и каталог иконок.

Миграция `0003_applications.sql` добавляется поверх этапа 2 и сохраняет пользователей и сессии. Полный контракт, ошибки и примеры запросов: [административное API каталога](docs/admin-api.md). Проверки включают конкурентную уникальность slug, повторную проверку сессии при изменениях, обновление существующей БД, восстановление файлов после сбоя, ограничения изображений и основные сценарии React.


## Релизы и дистрибутивы (этап 4)

Откройте приложение → **Релизы → Создать релиз**, задайте SemVer `1.2.0`. В черновике загрузите установщики для разных платформ. Drag & drop, реальный прогресс передачи, отмена, скачивание, копирование и серверная проверка SHA-256 доступны без перезагрузки. Комбинация платформа/формат/назначение в релизе уникальна: установщик и updater одного формата могут сосуществовать. Для Tauri допускается один updater на платформу. Новые релизы для архивных приложений запрещены; существующие черновики доступны. Изменения требуют admin и CSRF; operator просматривает и скачивает.

По умолчанию файл ограничен 2 GiB, запрос — 2 GiB + 1 MiB, ожидание порции данных — 120 секунд. Временный каталог находится в `storage.directory/.tmp`. Он должен быть на одном filesystem с постоянным хранилищем. Backend пишет и хеширует потоково, с ограниченным read-ahead multipart. Скачивание тоже потоковое. Весь файл не загружается в RAM.

SQLite и файловая система не атомарны: используются create_new, sync, атомарная установка постоянного имени без перезаписи и компенсационная очистка. Startup до listener проверяет наличие/размер referenced объектов и удаляет незавершённые/непривязанные серверные файлы. Отсутствующий referenced файл останавливает запуск для восстановления согласованной копии. Один сервер обслуживает БД и каталоги. Публикация и подписи добавлены на этапе 5; публичные скачивания и Range добавлены на этапе 6.

Полный [контракт, физическое хранение, аварийные сценарии, Nginx и резервное копирование](docs/releases.md). Для production обязательно согласуйте `client_max_body_size` с лимитом приложения и отключите `proxy_request_buffering` для потока загрузки. Резервируйте БД, каталог дистрибутивов и иконки согласованно при остановленном сервере. Бинарник можно заменять независимо от каталогов данных.


## Публикация и манифесты (этап 5)

В черновике выполните **Проверить готовность → Опубликовать → Подтвердить публикацию**. Сервер повторно проверяет файлы/SHA-256 и права. При конкурентном изменении релиза ответ 409 требует новой проверки. Новые артефакты можно добавлять к опубликованной версии; для updater обязательна `.sig`.

В приложении доступны URL-вкладки `/manifests`, `/history`, `/distribution` и `/integrations/tauri`. Администратор создаёт черновик, загружает файлы, проверяет готовность и публикует. Существующие опубликованные файлы неизменяемы; новые платформы и форматы можно добавлять в ту же версию.

Последний установщик выбирается независимо для платформы по SemVer среди published без prerelease. Например, macOS может использовать 0.6.0, а Windows — 0.5.0. При нескольких форматах скачивание без format получает 409; загрузка файлов разрешена.

```text
/{slug}/latest                         → страница выбора установщика
/{slug}/latest/windows-x86_64
/{slug}/latest/windows-aarch64
/{slug}/latest/darwin-aarch64
/{slug}/latest/darwin-x86_64
/{slug}/latest/linux-x86_64
/{slug}/latest/windows-x86_64?format=exe
/{slug}/releases/{version}/artifacts/{uuid}/download
/{slug}/manifest.json
/api/v1/updates/tauri/{slug}/{target}/{arch}/{currentVersion}
```

Манифест schema_version=2 содержит latest_by_target и историю версий с SHA-256, размерами и URL. Пустая история допустима. Tauri выбирает последнюю совместимую подписанную updater-версию для платформы, сохраняя Universal и защиту от downgrade. Поля и примеры: [публичное API](docs/public-distribution.md), [публикация](docs/release-management.md), [Tauri](docs/integrations/tauri.md).

Перед обновлением существующей базы выполните [проверку и явную политику миграции 0009](docs/migration-0009.md). Миграция сохраняет опубликованные релизы, подписи и файлы и останавливается при риске неявного расширения публичного доступа.

Standalone-приложения могут использовать один и тот же `installer` для ручного скачивания и обновлений: внешний JWS Ed25519 связывает UUID приложения, версию, платформу, размер и SHA-256. Ключ приложения и подпись задаются через admin API; `GET /api/v1/updates/standalone/{slug}/{target}?current_version=…` выдаёт только более новые подписанные файлы. Миграция `0010` сохраняет прежние роли, Tauri `.sig` и manifest v2. Порядок подписания, загрузки и независимой проверки: [Standalone-интеграция](docs/integrations/standalone.md) и [независимый HTTP/JWS-контракт](docs/integrations/standalone-protocol.md). Необязательный `kid` — проверяемый JWK thumbprint, совместимый с прежними подписями без идентификатора. Установка/перезапуск и ротация закреплённого ключа пока не реализованы.

## Публичное распространение (этап 6)

Сделайте приложение active/public, загрузите файлы в черновик и опубликуйте. В **Распространение** доступны готовые ссылки каждой платформы, копирование и диагностика HEAD. Публичная страница показывает актуальные установщики и историю без авторизации.

```sh
curl -I 'https://apps.veruna.systems/product/latest/windows-x86_64?format=msi'
curl -fL 'https://apps.veruna.systems/product/latest/linux-x86_64?format=deb' -o product.deb
curl -f 'https://apps.veruna.systems/product/manifest.json'
curl -i 'https://apps.veruna.systems/api/v1/updates/tauri/product/windows/x86_64/1.3.0'
```

Примеры предполагают реальные опубликованные файлы. Direct передаёт поток с GET/HEAD, Range/If-Range/ETag и ограничением конкурентных загрузок. Для Nginx задайте `download.delivery_mode=nginx` и установите [internal alias](deploy/nginx/README.md). URL конкретного UUID сохраняется после новых публикаций. Private/archived/draft недоступны публично; долгих публичных TTL нет. Дополнительная проверка Nginx: `python3 scripts/smoke_nginx.py` (Docker).
