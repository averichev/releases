# Архитектура Veruna Releases

## Область этапа 1

Платформа хранит и распространяет ПО разных продуктов и в дальнейшем управляет публикацией обновлений. Развёртывание предполагается в корне `https://apps.veruna.systems`. Текущий этап создаёт инфраструктуру; доменная функциональность намеренно отсутствует.

## Решение: модульный монолит

Один Cargo package содержит библиотеку для композиции и тестирования и единственный binary target. Rust workspace сейчас не нужен: нет отдельных исполняемых компонентов, независимо версионируемых библиотек или разных политик зависимостей. Границы выражены модулями. Если появится второй потребитель домена, подходящий модуль можно вынести в crate без изменения HTTP-контракта.

```text
.
├── Cargo.toml / Cargo.lock
├── build.rs                    проверка UI и отслеживание ресурсов сборки
├── src/
│   ├── main.rs                 запуск, listener, drain, остановка pool
│   ├── lib.rs                  composition root инфраструктуры
│   ├── config.rs               defaults → TOML → environment, валидация
│   ├── domain/                 будущие продуктовые модули и инварианты
│   ├── services/health.rs      сценарий проверки готовности
│   ├── repositories/health.rs  конкретная SQL-проверка
│   ├── infrastructure/         БД, storage, logging, shutdown
│   └── http/                   public/admin routers, DTO, ошибки, SPA
├── migrations/                 встроенные SQLx-миграции
├── frontend/                   React, TS, Ant Design, Vite
├── tests/                      HTTP, конфигурация, инфраструктура
├── scripts/                    сборка, проверки, standalone smoke
└── docs/
```

## Направление зависимостей

`HTTP → services → repositories → SQLx`; доменные правила используются сервисами и не знают о HTTP/SQL. Инициализация собирает реальные адаптеры из конфигурации. Не вводятся универсальный repository trait, отдельная абстракция над каждым запросом или runtime DI.

Сейчас health не является бизнес-сущностью: сервис принимает конкретный `SqlitePool` и вызывает конкретный репозиторий. Это сознательная простота, а не требование передавать пул во все будущие доменные функции. При появлении сценариев сервис получает только нужные ему репозитории и интерфейс хранилища.

`ArtifactStorage` отделяет операции с дистрибутивами от остального приложения. Сейчас единственная реальная операция — идемпотентная инициализация каталога через `LocalArtifactStorage`. Потоковые чтение/запись, метаданные, удаление и формат ключей будут добавлены вместе с настоящими сценариями. Нет фиктивных `upload`, `delete` или интерфейса S3 без потребителя. Trait использует нативный async/RPITIT и статическую диспетчеризацию; динамический registry провайдеров не нужен.

## HTTP и поток запроса

```text
Клиент → reverse proxy с TLS → Axum
  GET /api/v1/health → service → repository → SQLite → JSON
  /api/v1/admin[/...] → общий закрытый gate → 503 JSON
  /api[/...] без совпадения → 404 JSON
  /assets/<hash>.(js|css) → встроенный ресурс
  /admin[/...] или / → встроенный index.html → React Router
  прочие отсутствующие ресурсы → 404 JSON
```

Версионирование начинается с `/api/v1`; public router и admin router собираются отдельно. Gate административного router работает для всех методов, корневого пути и неизвестных вложенных путей. `503 administration_unavailable` означает, что подсистема ещё не доступна. Это не проверка пароля и не обещание существующей аутентификации. Следующий этап заменит gate реальной авторизацией и её тестами до добавления административных операций.

Панель `/admin` пока общедоступна, так как содержит только навигацию, описание будущих разделов и публичное состояние сервера. Пользовательские данные, учётные записи и токены не создаются. Будущая защита должна находиться на сервере.

Ошибки HTTP централизованы в `http/error.rs`:

```json
{"error":{"code":"not_found","message":"Resource not found"}}
```

Клиент видит стабильный код и безопасное сообщение; причина ошибки health записывается во внутренний лог. Неизвестное API не получает HTML. Неподдерживаемые методы — `405`; `GET`/`HEAD` поддерживаются для UI/assets. При добавлении JSON/query extractors их ошибки также необходимо привести к общему envelope: текущий этап не принимает входные бизнес-DTO.

`health` возвращает `200` только после успешного обращения к БД, иначе `503`. Он не проверяет возможность записи будущего файла, остаток места или внешние системы.

## SQLite и миграции

Параметры задаются через `SqliteConnectOptions` для каждого соединения:

- `foreign_keys = ON`;
- `journal_mode = WAL`;
- `synchronous = FULL` — более консервативная сохранность подтверждённых изменений ценой скорости записи;
- `busy_timeout = 5s` и ограниченный pool с 4 соединениями по умолчанию;
- `acquire_timeout` равен `busy_timeout`, чтобы ожидание соединения не было бесконечным.

WAL подходит для чтений параллельно с записью, но SQLite остаётся БД с одним писателем. Дальнейшие сценарии должны держать транзакции короткими. Несколько соединений не означают параллельные записи. Нужен локальный файловый диск, а не общий сетевой том для нескольких экземпляров.

Родительские каталоги создаются автоматически. `sqlx::migrate!` встраивает SQL в бинарник; миграции применяются до открытия listener. Baseline `0001_baseline.sql` фиксирует начальную точку и оставляет только `_sqlx_migrations`, без продуктовых таблиц. SQLx хранит версию/checksum и не повторяет успешно применённую миграцию. Применённые файлы не редактируются.

База и каталог артефактов — два независимых хранилища. Будущая загрузка потребует явного протокола восстановления между записью файла и транзакцией БД; текущий этап не притворяется, что эта атомарность уже существует.

## Будущие модули

Это границы ответственности для следующих этапов, а не текущая схема БД или набор полей:

| Сущность / модуль | Ответственность |
| --- | --- |
| Application / `application` | Идентичность и настройки распространяемого продукта |
| Release / `release` | Версия продукта, состояние и правила публикации |
| Artifact / `artifact` | Метаданные дистрибутива и связь с файловым хранилищем |
| Channel / `channel` | Каналы доставки и выбор доступного обновления |
| User / `user` | Административная идентичность и доступ |
| ApiToken / `api_token` | Доступ автоматизаций, область действия и отзыв |
| DownloadEvent / `download_event` | Факт скачивания и основа последующей статистики |

Не фиксируются заранее обязательность канала, уникальность версии, форматы версий, роли, retention, поля манифеста или платформы. Эти решения требуют конкретных сценариев. Доменные модули, миграции, сервисы, репозитории, HTTP и тесты добавляются небольшими вертикальными изменениями.

## Конфигурация, логирование, lifecycle

Порядок запуска: загрузить и проверить конфигурацию → настроить JSON logging → зарегистрировать сигналы → инициализировать storage → подключить SQLite → миграции → bind → принимать запросы. Конфигурация неизменна во время жизни процесса. Относительные пути интерпретируются относительно CWD; production использует абсолютные пути.

HTTP middleware логирует метод, путь, код ответа и длительность. Query string, тела, cookies и authorization headers не включаются. Перед добавлением секретов в пути потребуется отдельная политика редактирования пути или логирование шаблона маршрута.

SIGINT/SIGTERM инициируют graceful shutdown: закрыть приём соединений, дождаться текущих HTTP-запросов с пределом времени, закрыть SQLx pool с отдельным пределом. Нормальная остановка — код 0; ошибки и превышение таймаута — ненулевой код. На других ОС используется Ctrl+C. Миграции и инициализация должны закончиться до обслуживаемого состояния; аварийный startup завершается ошибкой.

## Сборка и frontend

`npm ci → TypeScript → Vite → cargo build`. Эта последовательность явная в скриптах и CI. `build.rs` не запускает subprocess/npm; он требует `frontend/dist/index.html` и следит за изменением `dist` и `migrations`.

`rust-embed` с `debug-embed` хранит assets в бинарнике во всех профилях. JS/CSS имеют имена с хешем и `Cache-Control: public, max-age=31536000, immutable`; HTML и favicon требуют перепроверки (`no-cache`). У ответов включён `nosniff`, поддерживается gzip по согласованию с клиентом. Прямое открытие вложенных `/admin/...` получает index.html; неизвестный frontend-маршрут показывает React 404. Пути с точкой вне реальных assets не используют SPA fallback. Новые загрузки и манифесты необходимо регистрировать явными серверными маршрутами.

Разработка интерфейса использует Vite HMR с прокси `/api`; production использует только Rust. CORS не включается: интерфейс и API имеют один origin. Префикс установки не поддерживается. Внешние runtime CDN/fonts отсутствуют.

Компромиссы: изменение UI требует пересборки и доставки бинарника; базовая Ant Design увеличивает bundle; один package задаёт модульные границы соглашениями и review, а не отдельными dependency graphs. На текущем масштабе это уменьшает стоимость сборки и поддержки.

## Основания и проверка

Решения опираются на официальные API [Axum](https://docs.rs/axum/0.8.9/axum/), [SQLx SQLite options](https://docs.rs/sqlx/0.8.6/sqlx/sqlite/struct.SqliteConnectOptions.html), [Vite](https://vite.dev/guide/) и [Ant Design](https://ant.design/docs/react/getting-started/). Фактическая совместимость фиксируется lock-файлами и проверяется сборкой.

Автоматические проверки покрывают контракт и отказ health, deny-all admin, изоляцию API от SPA, HEAD/assets, настройки SQLite на нескольких соединениях, идемпотентность миграций и приоритет конфигурации. Smoke-тест отдельно запускает бинарник без файлов frontend и миграций рядом с ним, проверяет выдачу JS/CSS и остановку SIGTERM. CI повторяет сборку, тесты, Clippy и smoke на Linux.
