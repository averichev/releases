# Архитектура Veruna Releases

## Область этапа 4

Платформа хранит и распространяет ПО разных продуктов и в дальнейшем управляет публикацией обновлений. Развёртывание предполагается в корне `https://apps.veruna.systems`. Реализованы идентичность, авторизация, пользователи, каталог Application, черновики Release и Artifact. Публикация, Channel и прочие сущности добавляются на следующих этапах.

## Решение: модульный монолит

Один Cargo package содержит библиотеку для композиции и тестирования и единственный binary target. Rust workspace сейчас не нужен: нет отдельных исполняемых компонентов, независимо версионируемых библиотек или разных политик зависимостей. Границы выражены модулями. Если появится второй потребитель домена, подходящий модуль можно вынести в crate без изменения HTTP-контракта.

```text
.
├── Cargo.toml / Cargo.lock
├── build.rs                    проверка UI и отслеживание ресурсов сборки
├── src/
│   ├── main.rs                 запуск, listener, drain, остановка pool
│   ├── lib.rs                  composition root инфраструктуры
│   ├── config.rs               defaults → TOML → environment, валидация
│   ├── domain/               User, Application, инварианты и валидация
│   ├── services/              health, authentication, users, sessions, applications и ошибки
│   ├── repositories/          конкретный SQL для health, users, sessions, applications
│   ├── infrastructure/         БД, storage, icons, logging, shutdown
│   └── http/                   public/admin routers, DTO, ошибки, SPA
├── migrations/                 встроенные SQLx-миграции
├── frontend/                   React, TS, Ant Design, Vite
├── tests/                      HTTP, конфигурация, инфраструктура
├── scripts/                    сборка, проверки, standalone smoke
└── docs/
```

## Направление зависимостей

`HTTP → services → repositories → SQLx`; доменные правила используются сервисами и не знают о HTTP/SQL. Инициализация собирает реальные адаптеры из конфигурации. Не вводятся универсальный repository trait, отдельная абстракция над каждым запросом или runtime DI.

Сейчас health не является бизнес-сущностью: сервис принимает конкретный `SqlitePool` и вызывает конкретный репозиторий. Это сознательная простота, а не требование передавать пул во все будущие доменные функции. При появлении сценариев сервис получает только нужные ему репозитории и интерфейс хранилища.

`ArtifactStorage` отделяет операции с дистрибутивами от остального приложения. Адаптер `LocalArtifactStorage` реализует потоковую запись/хеширование, атомарную установку имени без перезаписи, чтение, удаление, проверку SHA-256 и startup reconciliation. Нет интерфейса S3 без потребителя. Trait использует нативный async/RPITIT и статическую диспетчеризацию; динамический registry провайдеров не нужен.

## HTTP и поток запроса

```text
Клиент → reverse proxy с TLS → Axum
  GET /api/v1/health → service → repository → SQLite → JSON
  /api/v1/auth/... → authentication service → users/sessions repositories
  /api/v1/admin[/...] → session + CSRF + admin gate → user service → SQLite
  /api[/...] без совпадения → 404 JSON
  /assets/<hash>.(js|css) → встроенный ресурс
  /admin[/...] или / → встроенный index.html → React Router
  прочие отсутствующие ресурсы → 404 JSON
```

Версионирование начинается с `/api/v1`; public, auth и admin routers собираются отдельно. `health` остаётся публичным. Все административные пути и методы проходят `require_session`. Чтение каталога и иконок доступно оператору. Изменения каталога, управление пользователями и неизвестные административные пути дополнительно проходят `require_admin`. Методические fallback-обработчики устанавливаются до middleware, чтобы 405 не обходил gate.

Панель `/admin/...` отдаёт только HTML оболочки. Login и activation публичны; остальные страницы ждут `GET auth/me` до отображения навигации. Backend проверяет доступ независимо от React. Оператор не видит пункт «Пользователи» и получает 403 при прямом открытии/API-запросе.

Ошибки HTTP централизованы в `http/error.rs`:

```json
{"error":{"code":"not_found","message":"Resource not found"}}
```

Клиент видит стабильный код и безопасное сообщение; причина ошибки health записывается во внутренний лог. Неизвестное API не получает HTML. Неподдерживаемые методы — `405`; `GET`/`HEAD` поддерживаются для UI/assets. При добавлении JSON/query extractors их ошибки также необходимо привести к общему envelope: используются строгие DTO с deny_unknown_fields. Авторизация/пользователи ограничены 8 KiB, JSON каталога — 32 KiB, бинарная иконка — 2 МиБ.

`health` возвращает `200` только после успешного обращения к БД, иначе `503`. Он не проверяет возможность записи будущего файла, остаток места или внешние системы.

## SQLite и миграции

Параметры задаются через `SqliteConnectOptions` для каждого соединения:

- `foreign_keys = ON`;
- `journal_mode = WAL`;
- `synchronous = FULL` — более консервативная сохранность подтверждённых изменений ценой скорости записи;
- `busy_timeout = 5s` и ограниченный pool с 4 соединениями по умолчанию;
- `acquire_timeout` равен `busy_timeout`, чтобы ожидание соединения не было бесконечным.

WAL подходит для чтений параллельно с записью, но SQLite остаётся БД с одним писателем. Дальнейшие сценарии должны держать транзакции короткими. Несколько соединений не означают параллельные записи. Нужен локальный файловый диск, а не общий сетевой том для нескольких экземпляров.

Родительские каталоги создаются автоматически. `sqlx::migrate!` встраивает SQL в бинарник; миграции применяются до открытия listener. Baseline `0001_baseline.sql` фиксирует начальную точку и оставляет только `_sqlx_migrations`, без продуктовых таблиц. SQLx хранит версию/checksum и не повторяет успешно применённую миграцию. Применённые файлы не редактируются.

База и каталог артефактов — два независимых хранилища. Будущая загрузка потребует явного протокола восстановления между записью файла и транзакцией БД; текущий этап не притворяется, что эта атомарность уже существует.

## Будущие модули

Это границы ответственности для следующих этапов, а не текущая схема БД или набор полей:

| Сущность / модуль | Ответственность |
| --- | --- |
| Release / `release` | Версия продукта, состояние и правила публикации |
| Artifact / `artifact` | Метаданные дистрибутива и связь с файловым хранилищем |
| Channel / `channel` | Каналы доставки и выбор доступного обновления |
| ApiToken / `api_token` | Доступ автоматизаций, область действия и отзыв |
| DownloadEvent / `download_event` | Факт скачивания и основа последующей статистики |

Не фиксируются заранее обязательность канала, уникальность версии, форматы версий, роли, retention, поля манифеста или платформы. Эти решения требуют конкретных сценариев. Доменные модули, миграции, сервисы, репозитории, HTTP и тесты добавляются небольшими вертикальными изменениями.

## Конфигурация, логирование, lifecycle

Порядок запуска: загрузить и проверить конфигурацию → настроить JSON logging → зарегистрировать сигналы → инициализировать storage → подключить SQLite → миграции → bind → принимать запросы. Конфигурация неизменна во время жизни процесса. Относительные пути интерпретируются относительно CWD; production использует абсолютные пути.

HTTP middleware логирует метод, путь, код ответа и длительность. Query string, тела, cookies и authorization headers не включаются. Логируется только шаблон маршрута (либо `<unmatched>`), без фактических сегментов URI. Токены передаются в теле JSON; ссылки активации используют fragment, не query/path.

SIGINT/SIGTERM инициируют graceful shutdown: закрыть приём соединений, дождаться текущих HTTP-запросов с пределом времени, закрыть SQLx pool с отдельным пределом. Нормальная остановка — код 0; ошибки и превышение таймаута — ненулевой код. На других ОС используется Ctrl+C. Миграции и инициализация должны закончиться до обслуживаемого состояния; аварийный startup завершается ошибкой.

## Сборка и frontend

`npm ci → TypeScript → Vite → cargo build`. Эта последовательность явная в скриптах и CI. `build.rs` не запускает subprocess/npm; он требует `frontend/dist/index.html` и следит за изменением `dist` и `migrations`.

`rust-embed` с `debug-embed` хранит assets в бинарнике во всех профилях. JS/CSS имеют имена с хешем и `Cache-Control: public, max-age=31536000, immutable`; HTML и favicon требуют перепроверки (`no-cache`). У ответов включён `nosniff`, поддерживается gzip по согласованию с клиентом. Прямое открытие вложенных `/admin/...` получает index.html; неизвестный frontend-маршрут показывает React 404. Пути с точкой вне реальных assets не используют SPA fallback. Новые загрузки и манифесты необходимо регистрировать явными серверными маршрутами.

Разработка интерфейса использует Vite HMR с прокси `/api`; production использует только Rust. CORS не включается: интерфейс и API имеют один origin. Префикс установки не поддерживается. Внешние runtime CDN/fonts отсутствуют.

Компромиссы: изменение UI требует пересборки и доставки бинарника; базовая Ant Design увеличивает bundle; один package задаёт модульные границы соглашениями и review, а не отдельными dependency graphs. На текущем масштабе это уменьшает стоимость сборки и поддержки.

## Основания и проверка

Решения опираются на официальные API [Axum](https://docs.rs/axum/0.8.9/axum/), [SQLx SQLite options](https://docs.rs/sqlx/0.8.6/sqlx/sqlite/struct.SqliteConnectOptions.html), [Vite](https://vite.dev/guide/) и [Ant Design](https://ant.design/docs/react/getting-started/). Фактическая совместимость фиксируется lock-файлами и проверяется сборкой.

Автоматические проверки покрывают контракт и отказ health, session/admin gates, изоляцию API от SPA, HEAD/assets, настройки SQLite на нескольких соединениях, идемпотентность миграций и приоритет конфигурации. Smoke-тест отдельно запускает бинарник без файлов frontend и миграций рядом с ним, проверяет выдачу JS/CSS и остановку SIGTERM. CI повторяет сборку, тесты, Clippy и smoke на Linux.

## Авторизация и пользователи (этап 2)

Composition root `application_state` создаёт конкретные UsersRepository, SessionsRepository, Passwords, Authentication, Sessions и UserManagement. HTTP DTO не содержат password_hash; доменные User/Role/Status не зависят от SQLx или Axum. Сервисы координируют транзакции, SQL остаётся в репозиториях. `Passwords` в infrastructure выполняет Argon2id в spawn_blocking с общим semaphore на 4 операции; неизвестные логины проверяются против dummy-хеша с той же стоимостью. Пароль не входит в Debug-структуры и оборачивается в Zeroizing в hashing adapter.

Новая миграция `0002_identity.sql` добавляет users (UUID, NOCASE unique username, ограничения роли/статуса), sessions (хеш токена, сроки, FK), user_tokens (один действующий одноразовый токен на пользователя, purpose invitation/reset) и login_attempts (хеш логина/общий лимит, срок). `password_hash` nullable только для ещё не активированных учётных записей; CHECK запрещает active без пароля. Применённая baseline-миграция неизменна.

При входе сначала резервируется попытка в SQLite, затем проверяется пароль вне write-транзакции, затем под `BEGIN IMMEDIATE` повторно проверяются статус и неизменность хеша и создаётся новая сессия. Предъявленная старая cookie отзывается; новый случайный идентификатор исключает session fixation. `last_login_at` обновляется при успешном входе. Идентификаторы сессий и одноразовые токены — 32 байта из OS CSPRNG, в SQLite только SHA-256. Срок сессии абсолютный, хранится в БД и проверяется на каждом запросе, включая статус пользователя. Выход удаляет текущую сессию; пароль, блокировка, смена роли и административный отзыв удаляют все сессии пользователя. Неактуальные сессии очищаются при входах, число сессий ограничено 20 на пользователя.

Смена пароля проверяет текущий пароль, а затем повторно сверяет сессию и хеш внутри write-транзакции. Она также удаляет оставшиеся ссылки восстановления. Активация удаляет токен через условный DELETE RETURNING и устанавливает пароль в одной транзакции; параллельное использование может успешно завершиться только однажды. Новый токен атомарно заменяет старый. Заблокированные учётные записи нельзя активировать или восстановить; блокировка удаляет токены. При разблокировке неактивированной учётной записи статус становится invited, после чего администратор выдаёт новое приглашение.

Все изменения управления пользователями выполняются в коротких `BEGIN IMMEDIATE` транзакциях с повторной проверкой живой сессии и текущей роли действующего администратора. Триггеры BEFORE UPDATE/DELETE запрещают утрату последнего active admin, в том числе при конкурентных изменениях. Bootstrap проверяет наличие любого admin, вводит пароль вне транзакции и повторно проверяет admin под write-lock до вставки. CLI не требует HTTP listener или инициализации storage; пароль не принимается аргументом. Отдельный локальный `admin reset-password` выдаёт токен восстановления только для активного admin и закрывает потерю пароля единственного администратора. Этот сервисный entry point доступен только composition root CLI и никогда не подключается к HTTP. Сама установка пароля проходит через обычное атомарное потребление токена.

Для production `auth.public_origin` — HTTPS origin, из него детерминированно выбирается `__Host-` cookie с Secure. Приложение не доверяет ни одному proxy header, поэтому нет неоднозначного определения HTTPS или адреса клиента. TLS и доступность backend только со стороны proxy — ответственность развёртывания. Для loopback HTTP разработки допускается обычное имя cookie. Параметры конфигурации, их границы и пример Nginx описаны в README.

CSRF: все mutations требуют точный настроенный Origin и custom header X-Veruna-Request, защищённые mutations также X-CSRF-Token. CSRF-токен — domain-separated SHA-256 от случайного идентификатора сессии; возвращается login/me, сравнивается constant-time с вычисленным по HttpOnly cookie значением. База не хранит исходный секрет. Токен живёт только в памяти React и восстанавливается через me. SameSite=Lax — дополнительная защита. CORS не включён; обычная сторонняя форма не может выставить custom header, а сторонний JS не проходит preflight/проверку Origin. GET/HEAD не изменяют бизнес-состояние.

Лимит входа не основан на подделываемых proxy IP: 5 попыток на нормализованный логин и 100 суммарно за 300 секунд, резервирование атомарно до Argon2. Успешная попытка освобождает лимит; завершённые неуспехом и выполняющиеся попытки учитываются. Истёкшие записи удаляются при следующей попытке. Это простой консервативный предел для одного экземпляра и небольшой команды; распределённый rate limiter и ACL сейчас не нужны.

Ошибки сервисов отображаются в стабильный JSON в HTTP boundary. Внутренние причины логируются один раз там; пароли, cookie, csrf, токены, тела и произвольные URL не логируются. API использует no-store; UI/assets получают CSP, nosniff и no-referrer. Базовая панель не использует внешние runtime-ресурсы.

Тесты используют временную SQLite без внешних сервисов. Покрываются конкурентный bootstrap, CLI stdin, равенство ошибок неизвестного логина/пароля, SQL-инъекция, подмена роли в DTO, статусы и роли, CSRF (включая login), сессии и их истечение/отзыв, одноразовость/истечение/перевыдача токенов, восстановление и смена пароля, гонки потребления токена и последнего администратора. Frontend проверяет отсутствие закрытой навигации до me, восстановление вложенного маршрута, ошибки и истечение сессии, ограничение оператора, вход и CSRF-запросы.


## Каталог приложений (этап 3)

`domain/application.rs` содержит Application, Visibility, Status и ограничения полей без SQL/HTTP/файловой системы. `ApplicationCatalog` координирует конкретный `ApplicationsRepository` и инфраструктурный `IconStorage`; их подключает composition root. Репозиторий содержит весь SQL и преобразования строк в доменные типы. HTTP DTO отдельно формируют безопасный `icon_url`, внутренние пути не раскрываются. Контракт: [admin-api.md](admin-api.md).

`0003_applications.sql` создаёт только `applications`. UUID используется для будущих внешних ключей Release/Artifact/Channel. Slug — отдельный постоянный публичный идентификатор: lowercase ASCII, 1–64 символа, без дефиса на краях и без служебных имён. UNIQUE действует и для архива; триггер запрещает изменение UUID, slug и created_at. PATCH допускает только name, description и visibility; явный null, неизвестные и неизменяемые поля отвергаются. Active/private задаются по умолчанию. Статус и видимость независимы; архив и восстановление идемпотентны, физического удаления нет.

Список использует ограниченную пагинацию (до 100 строк), allowlist сортировок и связанные SQL-параметры. Внутреннее `name_search` содержит Unicode lowercase названия для поиска кириллицы без расширений SQLite. `instr` ищет буквальную подстроку, поэтому `%`/`_` не становятся wildcard. Индексы обслуживают фильтры, сортировку по названию и датам. Count и items читаются в одной read-транзакции со стабильной сортировкой по UUID при равных значениях. Это простой поиск для каталога; FTS пока не нужен.

Общий административный gate проверяет действующую сессию, статус пользователя и CSRF. Method routers чтения каталога/иконок доступны operator/admin; mutations дополнительно защищены require_admin. В каждой write-транзакции `BEGIN IMMEDIATE` сервис повторно проверяет сессию и актуальную роль через SessionsRepository. Предварительно проверенная или подделанная роль не заменяет эту проверку.

Иконки используют отдельный storage adapter в инфраструктурном слое. ArtifactStorage отвечает за дистрибутивы; общего framework хранилищ нет. `storage.icons_directory` по умолчанию `data/icons`; при startup canonicalize исключает совпадение и вложение с каталогом дистрибутивов. Пользователь никогда не задаёт файловый ключ. Генерируется UUID-key; `cap-std::fs::Dir` ограничивает lookup директорией и не позволяет выйти из неё через symlink. Чтение явно отвергает symlink. Сырой upload ограничен 2 МиБ до декодирования; PNG/JPEG/WebP определяются по содержимому и полностью декодируются с лимитом 1024×1024 и ограничением памяти. Два общих semaphore permits ограничивают обработку; filesystem и image CPU выполняются в spawn_blocking. Результат — RGBA PNG без пользовательских метаданных; у анимированного исходника используется первый кадр.

Протокол сохранения: случайный `.tmp` с create_new → запись → sync файла → rename в `.png` → sync каталога → короткая DB-транзакция с повторной авторизацией и заменой icon_key. Сбой до commit оставляет неиспользуемый объект, не разрушая текущую иконку. При неоднозначной ошибке commit новый файл не удаляется. При замене/удалении старые файлы сохраняются до следующего startup, чтобы не ломать параллельные чтения. `initialize` после миграций и до listener удаляет только сгенерированные временные и не referenced файлы; текущие ссылки сохраняются. Предполагается один сервер, обслуживающий локальную БД и каталоги. БД и файловая система не объявляются атомарными. Иконки выдаются только через защищённый GET, с image/png, nosniff и no-store; DTO содержит новый version URL после замены.

Frontend добавляет отдельную страницу создания, список карточек/таблицу и `/admin/applications/:id` с URL-вкладками обзора, релизов и настроек. Поиск, фильтры и пагинация хранятся в query string. Slug автоматически предлагается с транслитерацией до первого ручного изменения. По создании открывается подробная страница. Если последующая загрузка иконки не удалась, пользователь попадает в настройки уже созданного продукта с явной ошибкой. Права оператора отражаются в UI, но обеспечиваются backend. Публичные slug-маршруты, API релизов и фиктивные версии не добавляются.

Проверки этапа 3 покрывают HTTP-контракт, неизвестные/null поля, уникальность и неизменность идентичности, lifecycle, фильтры/поиск/пагинацию, CSRF/роли и отозванную сессию, конкурентные создания, изображения всех трёх форматов, ошибки декодирования и лимитов, symlink/traversal, startup cleanup и обновление существующей БД этапа 2. React-тесты проверяют создание, ручной slug, подробную страницу, редактирование, архив/восстановление, права, ошибки/повтор и поиск.


## Черновики релизов и артефакты (этап 4)

`domain/release.rs` и `domain/artifact.rs` отделены от HTTP, SQLx и диска. ReleaseManagement координирует ReleasesRepository и ArtifactStorage; ArtifactManagement — ArtifactsRepository, ReleasesRepository и тот же экземпляр хранилища с общим semaphore. Репозитории конкретны, без CRUD-framework. Composition root создаёт адаптеры и подключает новые method routers к существующей session/CSRF/admin границе. Изменения, включая завершение upload, перепроверяют действующую сессию и роль внутри короткого BEGIN IMMEDIATE. Длительные I/O и хеширование выполняются вне write-транзакции.

`0004_releases_artifacts.sql` добавляет только реальные сущности. Release ссылается на UUID приложения; Artifact — на UUID релиза. UUID/родитель/created_at релиза неизменны. Артефакты целиком неизменны и удаляются каскадно по релизу. Единственное состояние — draft с published_at=NULL. Версия проверяется semver, нормализуется trim/v; UNIQUE по приложению и версии без build metadata исключает неоднозначные версии одинакового приоритета. Сортировка metadata использует cmp_precedence. Будущая публикация сможет добавить состояния миграцией и ограничения изменений без смены UUID или storage keys. Подписи добавятся вместе с реальным updater use case к идентичности артефакта, без пустых полей заранее.

Storage keys — случайные UUID.blob, filename хранится только как метаданные. cap-std и no-follow открытие предотвращают traversal/symlink, каталог не имеет статической HTTP-выдачи. Временный каталог по умолчанию внутри корня, на той же файловой системе. Протокол: временная потоковая запись → sync → атомарный hard link без перезаписи → unlink временного имени → sync каталогов → DB-транзакция → commit. Это осознанная замена обычному rename с возможной перезаписью. SHA-256 и размер вычисляются при записи; повторного чтения нет до явной проверки целостности.

Guard компенсирует отказ/отмену до commit. Перед commit файл сохраняется при неоднозначном результате. Удаление сначала подтверждает изменение БД, потом удаляет файлы; отказ unlink оставляет безопасный orphan. До listener startup проверяет ссылки/размеры и очищает управляемые временные и непривязанные ключи. Отсутствующий referenced файл останавливает startup и требует ремонта/backup, записи не удаляются автоматически. Один сервер на локальной БД/хранилище; фонового сервиса и автопрореживания версий нет.

Axum Multipart получает отдельный request limit. Потоковый адаптер уступает управление после порции до 64 KiB, ограничивая read-ahead Multer; заголовкам выделен отдельный бюджет, metadata ограничены 128 байтами. Idle timeout, фактический лимит файла и request limit независимы. Скачивание использует ReaderStream, safe Content-Disposition filename* и octet-stream/no-store/nosniff. Четыре permits ограничивают uploads/verify. Filesystem capability operations и sync каталогов вынесены в spawn_blocking, файловые потоки используют Tokio. Детали API, конфигурации, сбоев и развёртывания: [releases.md](releases.md).

Frontend заменяет пустую вкладку релизов таблицей с поиском/пагинацией/сортировкой. Отдельный вложенный маршрут содержит metadata и artifacts. Ant Design Upload передаёт File через FormData/XHR без чтения в JS; upload progress приходит из transport events, отмена — AbortController. XHR использует общий CSRF/error/session-expired механизм. После 100% передачи UI ждёт подтверждённого ответа сервера. Mutations скрыты у operator и всегда защищены backend. Будущие кнопки публикации/каналов отсутствуют.
