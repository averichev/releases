# Архитектура «Релизы»

## Область этапа 6

Платформа хранит и распространяет ПО разных продуктов и управляет публикацией обновлений. Развёртывание предполагается в корне `https://apps.veruna.systems`. Реализованы идентичность, авторизация, каталог Application, Release/Artifact, публикация, история, универсальные манифесты и Tauri preview. Публичное распространение и production Tauri реализованы на этапе 6. Следующее расширение добавляет ApiToken и атомарную публикацию готового выпуска из CLI. DownloadEvent остаётся за границей реализации.

## Решение: модульный монолит

Один Cargo package содержит библиотеку для композиции и тестирования и единственный binary target. Rust workspace сейчас не нужен: нет отдельных исполняемых компонентов, независимо версионируемых библиотек или разных политик зависимостей. Границы выражены модулями. Если появится второй потребитель домена, подходящий модуль можно вынести в crate без изменения HTTP-контракта.

```text
.
├── Cargo.toml / Cargo.lock
├── build.rs                    проверка UI и отслеживание ресурсов сборки
├── src/
│   ├── main.rs                 запуск, listener, drain, остановка pool
│   ├── lib.rs                  composition root инфраструктуры
│   ├── config.rs               defaults → TOML → environment, валидация
│   ├── domain/               User, Application, инварианты и валидация
│   ├── services/              health, authentication, users, sessions, applications и ошибки
│   ├── repositories/          конкретный SQL для health, users, sessions, applications
│   ├── infrastructure/         БД, storage, icons, logging, shutdown
│   └── http/                   public/admin routers, DTO, ошибки, SPA
├── migrations/                 встроенные SQLx-миграции
├── frontend/                   React, TS, Ant Design, Vite
├── tests/                      HTTP, конфигурация, инфраструктура
├── scripts/                    сборка, проверки, standalone smoke
└── docs/
```

## Направление зависимостей

`http/api_publish` ограниченно разбирает multipart и переводит транспортные ссылки на части в состав выпуска; он не содержит SQL и не обращается к диску. `services/api_publishing` координирует ArtifactStorage, общие доменные валидаторы и PublicationValidator. Токен проверяется до чтения тела, затем повторно в короткой BEGIN IMMEDIATE вместе с активностью приложения, version_key и актуальностью product_id/ключей. Длительная передача, SHA-256, проверка JWS, flush/fsync и подготовка постоянных объектов выполняются до write lock. В этой транзакции создаются все Release/Artifact, один факт публикации и неизменяемый оригинальный manifest для повторов. Приватность приложения не меняется.

`api_publications` сохраняет нормализованный исходный состав, поэтому дополнение платформы через панель не ломает повтор первоначальной команды. Копии общей Windows-части получают разные storage key через capability-scoped hard links внутри ArtifactStorage: ограничения БД сохраняются, сетевые байты и хеширование не дублируются. Cleanup guards компенсируют ошибки/отмену; перед await commit освобождается удаление постоянных объектов, поскольку результат commit может быть неизвестен при отмене. Startup reconciliation удаляет безопасные orphan objects и проверяет ссылки до обслуживания запросов. Пакетные лимиты и ограничение параллельных запросов описаны в [CLI publication](cli-publication.md).

ApiToken имеет отдельный несекретный UUID, привязку к приложению и SHA-256 полного секрета из 32 случайных байт. Его единственное право — публикация нового выпуска. Управление токенами использует действующие admin-session/CSRF gates и повторную авторизацию в транзакции; Bearer-граница проверяет фактический HTTPS по доверенному loopback peer, даже при явных публичных URL. История содержит ровно одного автора: пользователя или токен. Миграция 0016 сохраняет прежних авторов, ID и timestamps; отозванные токены сохраняются для истории.

Standalone обновления используют тот же каталог `PublicDistribution` и общий SemVer-порядок, что manifest v2 и Tauri. `domain/standalone` определяет ограниченный JWS-профиль и проверяет Ed25519 через `jsonwebtoken`/RustCrypto; `ed25519-dalek` также проверяет валидность и отсутствие слабого публичного ключа. `services/standalone` отвечает только за допустимость подписанного кандидата конкретной платформы. Файлы проверяются через `ArtifactStorage`, URL строятся через request-scoped distribution с существующим origin middleware. В HTTP нет отдельной сортировки/логики выбора версий. Приватные ключи не принимаются и не хранятся.

`standalone_signature` — независимое opt-in назначение executable и прежних installer, а не отдельная роль или копия файла. Загрузка и привязка к черновику проверяют подпись под write lock по текущим ключу, версии и хешу. Публикация повторно проверяет подпись и полный SHA-256 вне write lock и сравнивает snapshot, включая ключ и новые метаданные, перед commit. `0010` добавляет nullable поля и ограничения, не переписывая существующие публикации; ключ закрепляется после появления подписанных артефактов. `0015` расширяет ограничение на executable заменой колонки подписи, сохраняя таблицу artifacts, внешние ключи, JWS и счётчики скачиваний. Расширение имени не участвует в проверке ABI executable: источником остаются target и подписанные os/arch. Необязательный защищённый `kid` проверяется как RFC 7638 thumbprint текущего доверенного ключа и вычисляется без нового состояния в БД; старые JWS без `kid` поддерживаются. Он оставляет точку расширения для будущего набора доверенных ключей, не вводя управление ротацией. Ротация доверия клиентов, TUF и установка за пределами текущей реализации. Независимый HTTP/JWS-контракт: [спецификация](integrations/standalone-protocol.md). Подробности и модель угроз: [standalone](integrations/standalone.md).

`HTTP → services → repositories → SQLx`; доменные правила используются сервисами и не знают о HTTP/SQL. Инициализация собирает реальные адаптеры из конфигурации. Не вводятся универсальный repository trait, отдельная абстракция над каждым запросом или runtime DI.

Сейчас health не является бизнес-сущностью: сервис принимает конкретный `SqlitePool` и вызывает конкретный репозиторий. Это сознательная простота, а не требование передавать пул во все будущие доменные функции. При появлении сценариев сервис получает только нужные ему репозитории и интерфейс хранилища.

`ArtifactStorage` отделяет операции с дистрибутивами от остального приложения. Адаптер `LocalArtifactStorage` реализует потоковую запись/хеширование, атомарную установку имени без перезаписи, чтение, удаление, проверку SHA-256 и startup reconciliation. Нет интерфейса S3 без потребителя. Trait использует нативный async/RPITIT и статическую диспетчеризацию; динамический registry провайдеров не нужен.

## HTTP и поток запроса

```text
Клиент → reverse proxy с TLS → Axum
  GET /api/v1/health → service → repository → SQLite → JSON
  /api/v1/auth/... → authentication service → users/sessions repositories
  /api/v1/admin[/...] → session + CSRF + admin gate → user service → SQLite
  /api[/...] без совпадения → 404 JSON
  /assets/<hash>.(js|css) → встроенный ресурс
  /admin[/...] или / → встроенный index.html → React Router
  прочие отсутствующие ресурсы → 404 JSON
```

Версионирование начинается с `/api/v1`; public, auth и admin routers собираются отдельно. `health` остаётся публичным. Все административные пути и методы проходят `require_session`. Чтение каталога и иконок доступно оператору. Изменения каталога, управление пользователями и неизвестные административные пути дополнительно проходят `require_admin`. Методические fallback-обработчики устанавливаются до middleware, чтобы 405 не обходил gate.

Панель `/admin/...` отдаёт только HTML оболочки. Login и activation публичны; остальные страницы ждут `GET auth/me` до отображения навигации. Backend проверяет доступ независимо от React. Оператор не видит пункт «Пользователи» и получает 403 при прямом открытии/API-запросе.

Ошибки HTTP централизованы в `http/error.rs`:

```json
{"error":{"code":"not_found","message":"Resource not found"}}
```

Клиент видит стабильный код и безопасное сообщение; причина ошибки health записывается во внутренний лог. Неизвестное API не получает HTML. Неподдерживаемые методы — `405`; `GET`/`HEAD` поддерживаются для UI/assets. При добавлении JSON/query extractors их ошибки также необходимо привести к общему envelope: используются строгие DTO с deny_unknown_fields. Авторизация/пользователи ограничены 8 KiB, JSON каталога — 32 KiB, бинарная иконка — 2 МиБ.

`health` возвращает `200` только после успешного обращения к БД, иначе `503`. Он не проверяет возможность записи будущего файла, остаток места или внешние системы.

## SQLite и миграции

Параметры задаются через `SqliteConnectOptions` для каждого соединения:

- `foreign_keys = ON`;
- `journal_mode = WAL`;
- `synchronous = FULL` — более консервативная сохранность подтверждённых изменений ценой скорости записи;
- `busy_timeout = 5s` и ограниченный pool с 4 соединениями по умолчанию;
- `acquire_timeout` равен `busy_timeout`, чтобы ожидание соединения не было бесконечным.

WAL подходит для чтений параллельно с записью, но SQLite остаётся БД с одним писателем. Дальнейшие сценарии должны держать транзакции короткими. Несколько соединений не означают параллельные записи. Нужен локальный файловый диск, а не общий сетевой том для нескольких экземпляров.

Родительские каталоги создаются автоматически. `sqlx::migrate!` встраивает SQL в бинарник; миграции применяются до открытия listener. Baseline `0001_baseline.sql` фиксирует начальную точку и оставляет только `_sqlx_migrations`, без продуктовых таблиц. SQLx хранит версию/checksum и не повторяет успешно применённую миграцию. Применённые файлы не редактируются.

База и каталог артефактов — два независимых хранилища. Потоковая загрузка использует протокол восстановления, описанный в разделе этапа 4; атомарность БД с файловой системой не предполагается.

## Конфигурация, логирование, lifecycle

Порядок запуска: загрузить и проверить конфигурацию → настроить JSON logging → зарегистрировать сигналы → инициализировать storage → подключить SQLite → миграции → bind → создать HTTP-состояние → принимать запросы → открыть локальную панель в браузере. `infrastructure::startup` сохраняет занятый listener, а не делает отдельную проверку доступности порта. При `AddrInUse` и `server.auto_port` ОС выбирает свободный порт только для loopback с обоими origin, совпадающими с HTTP bind. Фактический адрес и оба origin согласуются до создания сервисов: CSRF и download URL используют один выбранный порт. Для reverse proxy, Vite, внешних origin и wildcard bind порт фиксирован. После создания HTTP-состояния конфигурация неизменна. Относительные пути интерпретируются относительно CWD; production использует абсолютные пути.

`server.open_browser` включает системный асинхронный launcher (`open`, `rundll32.exe`, `xdg-open`) без shell только при совпадении локального HTTP-адреса с auth origin. Открытие следует за первым poll HTTP-сервера; launcher имеет таймаут, ошибка не останавливает сервер, URL панели выводится в консоль. Для headless можно отключить открытие. Административные CLI-команды не запускают listener и браузер.

HTTP middleware логирует метод, путь, код ответа и длительность. Query string, тела, cookies и authorization headers не включаются. Логируется только шаблон маршрута (либо `<unmatched>`), без фактических сегментов URI. Одноразовые токены активации передаются в JSON и fragment ссылок; токены публикации — только в Authorization Bearer, без query/path.

SIGINT/SIGTERM инициируют graceful shutdown: закрыть приём соединений, дождаться текущих HTTP-запросов с пределом времени, закрыть SQLx pool с отдельным пределом. Нормальная остановка — код 0; ошибки и превышение таймаута — ненулевой код. На других ОС используется Ctrl+C. Миграции и инициализация должны закончиться до обслуживаемого состояния; аварийный startup завершается ошибкой.

## Сборка и frontend

`npm ci → TypeScript → Vite → cargo build`. Эта последовательность явная в скриптах и CI. `build.rs` не запускает subprocess/npm; он требует `frontend/dist/index.html` и следит за изменением `dist` и `migrations`.

Для `veruna-pack build` конфигурация `release.toml` указывает на `deploy/self-update-identity.json`. VerunaPack проверяет ключ издателя по `updates.public_key`, а `build.rs` встраивает этот же ключ и UUID из Git-снимка вместе с версией из `VERUNA_RELEASE_VERSION`. Проверка нативного файла вызывает `--version` до загрузки настроек сервера. Проверенный комплект сохраняется в `releases/<версия>/`.

`make release` вызывает `scripts/release.sh` → `scripts/release.py` (Python 3.11+, stdlib) на macOS. Версия рассчитывается по самому большому достижимому стабильному тегу `vX.Y.Z` и максимальному Conventional Commits impact после него: fix/perf/revert → patch, feat → minor, breaking → major (до 1.0 → minor). Без тегов используется Cargo-версия и вся история; HEAD с тегом сохраняет его версию. Только технические коммиты без impact не выпускают релиз. `make release-plan` показывает расчёт без мутаций.

Выпуск требует чистое рабочее дерево и полную Git-историю. Advisory lock в Git-каталоге запрещает параллельный выпуск в одном checkout. Python один раз собирает UI, затем Linux x86_64 (musl через cargo-zigbuild/Zig), Windows x86_64 (GNU через MinGW) и macOS ARM64 (Apple toolchain). Сохранены явно выбранный rustup toolchain, `--locked`, `--target-dir target`, лимит файлов Zig и права исполнения. Build-time `RELEASE_VERSION` проходит SemVer-проверку в build.rs и задаёт `crate::VERSION` для health и логов; build.rs отслеживает изменение переменной. Cargo/frontend manifests и lock-файлы не меняются, без override используется CARGO_PKG_VERSION.

Все бинарники сначала помещаются во временный каталог. Перед атомарным переименованием в `dist/releases/<version>/` повторно проверяются чистота и Git-план; рядом с бинарниками сохраняются `release.json` (версия/коммит/предыдущий тег) и SHA-256 всех файлов. Только после успешной установки каталога создаётся локальный лёгкий тег `v<version>` на исходном коммите. При наличии ключа издателя скрипт подписывает каждый бинарник и проверяет его JWS до сохранения каталога. Старые каталоги не меняются. Повтор проверяет метаданные/суммы и не пересобирает тот же коммит; при сбое создания тега готовый каталог позволяет завершить шаг повтором. Частичная сборка не получает каталога/тега. Старые каталоги без метаданных не считаются состоянием версионирования и не перезаписываются. macOS сохраняет расширение `.tool` для запуска из Finder. `scripts/build.sh` остаётся обычной сборкой текущей ОС.

`rust-embed` с `debug-embed` хранит assets в бинарнике во всех профилях. JS/CSS имеют имена с хешем и `Cache-Control: public, max-age=31536000, immutable`; HTML и favicon требуют перепроверки (`no-cache`). У ответов включён `nosniff`, поддерживается gzip по согласованию с клиентом. Прямое открытие вложенных `/admin/...` получает index.html; неизвестный frontend-маршрут показывает React 404. Пути с точкой вне реальных assets не используют SPA fallback. Новые загрузки и манифесты необходимо регистрировать явными серверными маршрутами.

Визуальное имя платформы — «Релизы». `Brand` объединяет локальные SVG знака «Выход» и надписи в контурах; Vite выдаёт имена с хешем под `/assets/`. Системные иконки доступны по явным GET/HEAD-маршрутам `/favicon.svg`, `/favicon.ico`, `/apple-touch-icon.png` с `no-cache`. Они не используют разрешение публичного приложения по slug. Исходные варианты и экспортные размеры находятся в `assets/brand`, в сборку UI включены только выбранные файлы. Технические идентификаторы, cookie, заголовки, имена файлов конфигурации и бинарника от визуального имени не зависят.

Разработка интерфейса использует Vite HMR с прокси `/api`; production использует только Rust. CORS не включается: интерфейс и API имеют один origin. Префикс установки не поддерживается. Внешние runtime CDN/fonts отсутствуют.

Компромиссы: изменение UI требует пересборки и доставки бинарника; базовая Ant Design увеличивает bundle; один package задаёт модульные границы соглашениями и review, а не отдельными dependency graphs. На текущем масштабе это уменьшает стоимость сборки и поддержки.

## Основания и проверка

Решения опираются на официальные API [Axum](https://docs.rs/axum/0.8.9/axum/), [SQLx SQLite options](https://docs.rs/sqlx/0.8.6/sqlx/sqlite/struct.SqliteConnectOptions.html), [Vite](https://vite.dev/guide/) и [Ant Design](https://ant.design/docs/react/getting-started/). Фактическая совместимость фиксируется lock-файлами и проверяется сборкой.

Автоматические проверки покрывают контракт и отказ health, session/admin gates, изоляцию API от SPA, HEAD/assets, настройки SQLite на нескольких соединениях, идемпотентность миграций и приоритет конфигурации. Smoke-тест отдельно запускает бинарник без файлов frontend и миграций рядом с ним, проверяет выдачу JS/CSS и остановку SIGTERM. CI повторяет сборку, тесты, Clippy и smoke на Linux.

## Авторизация и пользователи (этап 2)

Composition root `application_state` создаёт конкретные UsersRepository, SessionsRepository, Passwords, Authentication, Sessions и UserManagement. HTTP DTO не содержат password_hash; доменные User/Role/Status не зависят от SQLx или Axum. Сервисы координируют транзакции, SQL остаётся в репозиториях. `Passwords` в infrastructure выполняет Argon2id в spawn_blocking с общим semaphore на 4 операции; неизвестные логины проверяются против dummy-хеша с той же стоимостью. Пароль не входит в Debug-структуры и оборачивается в Zeroizing в hashing adapter.

Новая миграция `0002_identity.sql` добавляет users (UUID, NOCASE unique username, ограничения роли/статуса), sessions (хеш токена, сроки, FK), user_tokens (один действующий одноразовый токен на пользователя, purpose invitation/reset) и login_attempts (хеш логина/общий лимит, срок). `password_hash` nullable только для ещё не активированных учётных записей; CHECK запрещает active без пароля. Применённая baseline-миграция неизменна.

При входе сначала резервируется попытка в SQLite, затем проверяется пароль вне write-транзакции, затем под `BEGIN IMMEDIATE` повторно проверяются статус и неизменность хеша и создаётся новая сессия. Предъявленная старая cookie отзывается; новый случайный идентификатор исключает session fixation. `last_login_at` обновляется при успешном входе. Идентификаторы сессий и одноразовые токены — 32 байта из OS CSPRNG, в SQLite только SHA-256. Срок сессии абсолютный, хранится в БД и проверяется на каждом запросе, включая статус пользователя. Выход удаляет текущую сессию; пароль, блокировка, смена роли и административный отзыв удаляют все сессии пользователя. Неактуальные сессии очищаются при входах, число сессий ограничено 20 на пользователя.

Смена пароля проверяет текущий пароль, а затем повторно сверяет сессию и хеш внутри write-транзакции. Она также удаляет оставшиеся ссылки восстановления. Активация удаляет токен через условный DELETE RETURNING и устанавливает пароль в одной транзакции; параллельное использование может успешно завершиться только однажды. Новый токен атомарно заменяет старый. Заблокированные учётные записи нельзя активировать или восстановить; блокировка удаляет токены. При разблокировке неактивированной учётной записи статус становится invited, после чего администратор выдаёт новое приглашение.

Все изменения управления пользователями выполняются в коротких `BEGIN IMMEDIATE` транзакциях с повторной проверкой живой сессии и текущей роли действующего администратора. Триггеры BEFORE UPDATE/DELETE запрещают утрату последнего active admin, в том числе при конкурентных изменениях. Bootstrap проверяет наличие любого admin, вводит пароль вне транзакции и повторно проверяет admin под write-lock до вставки. CLI не требует HTTP listener или инициализации storage; пароль не принимается аргументом. Отдельный локальный `admin reset-password` выдаёт токен восстановления только для активного admin и закрывает потерю пароля единственного администратора. Этот сервисный entry point доступен только composition root CLI и никогда не подключается к HTTP. Сама установка пароля проходит через обычное атомарное потребление токена.

По умолчанию `auth.public_origin` и `download.public_base_url` пусты. `http/origin` получает домен из проверенного Host и HTTPS из единственного X-Forwarded-Proto только от loopback TCP peer (ConnectInfo задаётся composition root). Остальные proxy headers игнорируются; публичный HTTP-домен отклоняется. Middleware один раз клонирует AppState для запроса и заполняет URL в auth/distribution и зависимых manifest/updater/tauri services. Общее состояние, SQLite и semaphore остаются общими, домен запроса не сохраняется. HTTP-обработчики и session/CSRF middleware используют эту копию через Extension. Явные URL в конфигурации имеют приоритет и не зависят от запроса. Для HTTPS выбирается `__Host-` cookie с Secure. TLS и доступность backend только со стороны proxy — ответственность развёртывания. Для loopback HTTP разработки допускается обычное имя cookie. Параметры конфигурации, их границы и пример Nginx описаны в README.

CSRF: все mutations требуют точный настроенный Origin и custom header X-Veruna-Request, защищённые mutations также X-CSRF-Token. CSRF-токен — domain-separated SHA-256 от случайного идентификатора сессии; возвращается login/me, сравнивается constant-time с вычисленным по HttpOnly cookie значением. База не хранит исходный секрет. Токен живёт только в памяти React и восстанавливается через me. SameSite=Lax — дополнительная защита. CORS не включён; обычная сторонняя форма не может выставить custom header, а сторонний JS не проходит preflight/проверку Origin. GET/HEAD не изменяют бизнес-состояние.

Лимит входа не основан на подделываемых proxy IP: 5 попыток на нормализованный логин и 100 суммарно за 300 секунд, резервирование атомарно до Argon2. Успешная попытка освобождает лимит; завершённые неуспехом и выполняющиеся попытки учитываются. Истёкшие записи удаляются при следующей попытке. Это простой консервативный предел для одного экземпляра и небольшой команды; распределённый rate limiter и ACL сейчас не нужны.

Ошибки сервисов отображаются в стабильный JSON в HTTP boundary. Внутренние причины логируются один раз там; пароли, cookie, csrf, токены, тела и произвольные URL не логируются. API использует no-store; UI/assets получают CSP, nosniff и no-referrer. Базовая панель не использует внешние runtime-ресурсы.

Тесты используют временную SQLite без внешних сервисов. Покрываются конкурентный bootstrap, CLI stdin, равенство ошибок неизвестного логина/пароля, SQL-инъекция, подмена роли в DTO, статусы и роли, CSRF (включая login), сессии и их истечение/отзыв, одноразовость/истечение/перевыдача токенов, восстановление и смена пароля, гонки потребления токена и последнего администратора. Frontend проверяет отсутствие закрытой навигации до me, восстановление вложенного маршрута, ошибки и истечение сессии, ограничение оператора, вход и CSRF-запросы.

## Каталог приложений (этап 3)

`domain/application.rs` содержит Application, Visibility, Status и ограничения полей без SQL/HTTP/файловой системы. `ApplicationCatalog` координирует конкретный `ApplicationsRepository` и инфраструктурный `IconStorage`; их подключает composition root. Репозиторий содержит весь SQL и преобразования строк в доменные типы. HTTP DTO отдельно формируют безопасный `icon_url`, внутренние пути не раскрываются. Контракт: [admin-api.md](admin-api.md).

`0003_applications.sql` создаёт только `applications`. UUID используется для будущих внешних ключей Release/Artifact. Slug — отдельный постоянный публичный идентификатор: lowercase ASCII, 1–64 символа, без дефиса на краях и без служебных имён. UNIQUE действует и для архива; триггер запрещает изменение UUID, slug и created_at. PATCH допускает только name, description и visibility; явный null, неизвестные и неизменяемые поля отвергаются. Active/private задаются по умолчанию. Статус и видимость независимы; архив и восстановление идемпотентны, физического удаления нет.

Список использует ограниченную пагинацию (до 100 строк), allowlist сортировок и связанные SQL-параметры. Внутреннее `name_search` содержит Unicode lowercase названия для поиска кириллицы без расширений SQLite. `instr` ищет буквальную подстроку, поэтому `%`/`_` не становятся wildcard. Индексы обслуживают фильтры, сортировку по названию и датам. Count и items читаются в одной read-транзакции со стабильной сортировкой по UUID при равных значениях. Это простой поиск для каталога; FTS пока не нужен.

Общий административный gate проверяет действующую сессию, статус пользователя и CSRF. Method routers чтения каталога/иконок доступны operator/admin; mutations дополнительно защищены require_admin. В каждой write-транзакции `BEGIN IMMEDIATE` сервис повторно проверяет сессию и актуальную роль через SessionsRepository. Предварительно проверенная или подделанная роль не заменяет эту проверку.

Иконки используют отдельный storage adapter в инфраструктурном слое. ArtifactStorage отвечает за дистрибутивы; общего framework хранилищ нет. `storage.icons_directory` по умолчанию `data/icons`; при startup canonicalize исключает совпадение и вложение с каталогом дистрибутивов. Пользователь никогда не задаёт файловый ключ. Генерируется UUID-key; `cap-std::fs::Dir` ограничивает lookup директорией и не позволяет выйти из неё через symlink. Чтение явно отвергает symlink. Сырой upload ограничен 2 МиБ до декодирования; PNG/JPEG/WebP определяются по содержимому и полностью декодируются с лимитом 1024×1024 и ограничением памяти. Два общих semaphore permits ограничивают обработку; filesystem и image CPU выполняются в spawn_blocking. Результат для растра — RGBA PNG без пользовательских метаданных; у анимированного исходника используется первый кадр. SVG проходит ограниченный XML-разбор (без DTD, максимум 64 уровня, 200 атрибутов на элемент, 100000 событий) и очистку через `svg-hush`. Выход ограничен 5 МиБ. SVG сохраняется векторным, без скриптов, обработчиков событий и встроенного HTML; стандартные растровые data URL разрешены. HTTP-адаптер формирует MIME по проверенному формату объекта, выдаёт sandbox CSP с запретом скриптов и сетевых ресурсов. Общая CSP задаётся только при отсутствии специальной политики ответа; blob разрешён для предпросмотра выбранной иконки в панели.

Протокол сохранения: случайный `.tmp` с create_new → запись → sync файла → rename в `.png` или `.svg` → sync каталога → короткая DB-транзакция с повторной авторизацией и заменой icon_key. Сбой до commit оставляет неиспользуемый объект, не разрушая текущую иконку. При неоднозначной ошибке commit новый файл не удаляется. При замене/удалении старые файлы сохраняются до следующего startup, чтобы не ломать параллельные чтения. `initialize` после миграций и до listener удаляет только сгенерированные временные и не referenced файлы; текущие ссылки сохраняются. Предполагается один сервер, обслуживающий локальную БД и каталоги. БД и файловая система не объявляются атомарными. Административная выдача защищена сессией, публичная проверяет active/public; обе используют IconStorage, правильный MIME, nosniff и no-store. DTO содержит новый version URL после замены. Миграция 0014 расширяет CHECK icon_key до двух форматов через замену одного столбца с копированием данных, сохраняя таблицу, внешние ключи, индексы и триггеры идентичности.

Frontend добавляет отдельную страницу создания, список карточек/таблицу и `/admin/applications/:id` с URL-вкладками обзора, релизов и настроек. Поиск, фильтры и пагинация хранятся в query string. Slug автоматически предлагается с транслитерацией до первого ручного изменения. По создании открывается подробная страница. Если последующая загрузка иконки не удалась, пользователь попадает в настройки уже созданного продукта с явной ошибкой. Права оператора отражаются в UI, но обеспечиваются backend. Публичные slug-маршруты, API релизов и фиктивные версии не добавляются.

Проверки этапа 3 покрывают HTTP-контракт, неизвестные/null поля, уникальность и неизменность идентичности, lifecycle, фильтры/поиск/пагинацию, CSRF/роли и отозванную сессию, конкурентные создания, изображения всех трёх форматов, ошибки декодирования и лимитов, symlink/traversal, startup cleanup и обновление существующей БД этапа 2. React-тесты проверяют создание, ручной slug, подробную страницу, редактирование, архив/восстановление, права, ошибки/повтор и поиск.

## Черновики релизов и артефакты (этап 4)

`domain/release.rs` и `domain/artifact.rs` отделены от HTTP, SQLx и диска. ReleaseManagement координирует ReleasesRepository и ArtifactStorage; ArtifactManagement — ArtifactsRepository, ReleasesRepository и тот же экземпляр хранилища с общим semaphore. Репозитории конкретны, без CRUD-framework. Composition root создаёт адаптеры и подключает новые method routers к существующей session/CSRF/admin границе. Изменения, включая завершение upload, перепроверяют действующую сессию и роль внутри короткого BEGIN IMMEDIATE. Длительные I/O и хеширование выполняются вне write-транзакции.

`0004_releases_artifacts.sql` добавляет только реальные сущности. Release ссылается на UUID приложения; Artifact — на UUID релиза. UUID/родитель/created_at релиза неизменны. Артефакты целиком неизменны и удаляются каскадно по релизу. Единственное состояние — draft с published_at=NULL. Версия проверяется semver, нормализуется trim/v; UNIQUE по приложению и версии без build metadata исключает неоднозначные версии одинакового приоритета. Сортировка metadata использует cmp_precedence. Будущая публикация сможет добавить состояния миграцией и ограничения изменений без смены UUID или storage keys. Подписи добавятся вместе с реальным updater use case к идентичности артефакта, без пустых полей заранее.

Storage keys — случайные UUID.blob, filename хранится только как метаданные. cap-std и no-follow открытие предотвращают traversal/symlink, каталог не имеет статической HTTP-выдачи. Временный каталог по умолчанию внутри корня, на той же файловой системе. Протокол: временная потоковая запись → sync → атомарный hard link без перезаписи → unlink временного имени → sync каталогов → DB-транзакция → commit. Это осознанная замена обычному rename с возможной перезаписью. SHA-256 и размер вычисляются при записи; повторного чтения нет до явной проверки целостности.

Guard компенсирует отказ/отмену до commit. Перед commit файл сохраняется при неоднозначном результате. Удаление сначала подтверждает изменение БД, потом удаляет файлы; отказ unlink оставляет безопасный orphan. До listener startup проверяет ссылки/размеры и очищает управляемые временные и непривязанные ключи. Отсутствующий referenced файл останавливает startup и требует ремонта/backup, записи не удаляются автоматически. Один сервер на локальной БД/хранилище; фонового сервиса и автопрореживания версий нет.

Axum Multipart получает отдельный request limit. Потоковый адаптер уступает управление после порции до 64 KiB, ограничивая read-ahead Multer; заголовкам выделен отдельный бюджет, metadata ограничены 128 байтами. Idle timeout, фактический лимит файла и request limit независимы. Скачивание использует ReaderStream, safe Content-Disposition filename* и octet-stream/no-store/nosniff. Четыре permits ограничивают uploads/verify. Filesystem capability operations и sync каталогов вынесены в spawn_blocking, файловые потоки используют Tokio. Детали API, конфигурации, сбоев и развёртывания: [releases.md](releases.md).

## Публикация и представления обновлений (этап 5)

Validator получает read snapshot и проверяет файлы только через ArtifactStorage, вне write lock. Snapshot release/artifacts и ожидаемые revision проверяются заново под BEGIN IMMEDIATE вместе с живой сессией/admin и статусом приложения. Статус, дата публикации, revision и history коммитятся атомарно. Revision не зависит от точности timestamp. Сами published данные/файлы защищены как сервисными проверками, так и SQLite triggers; первый published_at не меняется. Внешняя запись в файлы владельцем диска остаётся операционной границей: каталог доступен только сервисному пользователю, повреждения обнаруживаются хешированием.

`ManifestGeneration` строит schema_version=2 из опубликованных Release/Artifact. PublicDistribution читает согласованный каталог и сортирует SemVer, latest_by_target считается до ограничения истории. Public добавляет download_url, private preview опускает его. ETag зависит от всего JSON; независимого JSON-хранилища нет.

`services/updater` нормализует Tauri targets и сравнивает SemVer precedence, выбирает только явно назначенный совместимый updater с сохранённым содержимым .sig. Сервис выбирает из согласованного каталога PublicDistribution.published, упорядоченного по SemVer. Синтаксический parser minisign не заменяет проверку подписи клиентским ключом. Публичный adapter отдаёт 200 либо 204, неправильная конфигурация не рекламируется как обновление. Admin preview диагностирует причину.

## Распространение (этап 6)

Для ручного скачивания `Artifact.target` может обозначать только ОС (`linux`, `darwin`, `windows`). Издатель указывает совместимость при загрузке, поэтому один релиз может содержать разные `install.sh` для Linux и macOS. Страница скачивания фильтрует файлы по ОС и типу. В прямых ссылках target сопоставляется точно. Подписанные обновления используют наборы платформ своих протоколов.

`select_artifact` применяет target/format/purpose, по умолчанию installer. Единственный кандидат выбирается автоматически, неоднозначность даёт 409. /latest/{target} и version URL перенаправляют 307 на точный UUID; /latest перенаправляет на страницу выбора. Канонический маршрут проверяет slug/версию/UUID, public/active/published и владельца артефакта.

`http/delivery` содержит HTTP preconditions, одиночные Range и заголовки. Оно не читает диск напрямую: ArtifactStorage выдаёт проверенный файловый дескриптор и доверенный internal URI. Direct ReaderStream ограничен 64 КиБ и take(length), body владеет permit/file, disconnect освобождает ресурсы. HEAD/304/412/416 не передают файл. Файловые метаданные используют u64, тест с разреженным 3 GiB файлом не выделяет гигабайты RAM.

Nginx — альтернативный delivery adapter в том же бинарнике. После проверки Rust отдаёт X-Accel-Redirect на строгий internal alias, Nginx выполняет sendfile/range; static storage недоступен напрямую. Оба режима используют ETag mtime/length для неизменяемых объектов и private/no-cache/must-revalidate. Полное хеширование остаётся при хранении/публикации и явном verify; публичный GET/HEAD/manifest/updater проверяют существование/тип/размер без O(file size). Нельзя обнаружить внешнюю порчу того же размера при каждом HEAD: запись разрешена только доверенному сервису, backup сохраняет содержимое/mtime.

Публичные React-маршруты отделены от AuthProvider и административного layout. /{slug} — отдельный серверный document handler с проверкой публичности; ошибки API/файлов не попадают в SPA fallback. Явные /admin и /admin/* сохраняют вложенные страницы панели, /favicon.svg и /index.html — встроенные assets. В панели добавлены /distribution, ссылки опубликованных файлов, готовность Tauri и диагностика GET манифеста + HEAD по allowlisted маршрутам текущего сервиса. Произвольных сетевых диагностических запросов сервер не выполняет.

Контракт и кеширование: [public-distribution.md](public-distribution.md). Nginx и права: [deploy/nginx](../deploy/nginx/README.md). Tauri: [integrations/tauri.md](integrations/tauri.md). CI/CD, S3/CDN или нового frontend/backend процесса этап не добавляет.

Последующее расширение: `http/delivery` регистрирует начало публичного GET/Range с нулевого байта через PublicDistribution после всех проверок и до выдачи потока/X-Accel. DistributionRepository атомарно перепроверяет published/public/active и ownership и увеличивает единственный SQLite-счётчик артефакта. Итоги Release/Application вычисляются SQL SUM в конкретных репозиториях. Отдельного сервиса аналитики, очереди или журнала DownloadEvent нет. Счётчики доступны через session-защищённые административные DTO; публичные manifest/ETag не меняются. [Правила метрики](public-distribution.md#счётчики-скачиваний), [схема](data-model.md#artifact_download_counts).

## Настройка Tauri-интеграции

`/admin/applications/:id/integrations/tauri` содержит русскоязычный мастер. Шаг и пакетный менеджер сохраняются в URL. Клиентский пример хранится в docs/integrations/tauri/client.ts и импортируется в интерфейс как текст; подсветка кода встроена локально.

Миграция `0007_tauri_integration.sql` добавляет nullable `applications.tauri_public_key` с ограничением размера. Это публичная настройка реального приложения, не новая сущность секретов. `domain/tauri` проверяет Tauri CLI envelope публичного minisign-пакета; приватные пакеты не принимаются. `ApplicationCatalog.set_tauri_key` использует существующий write lock и повторную проверку действующей admin-сессии в транзакции. GET доступен оператору; PUT проходит admin/session/CSRF. Значение не включается в публичное API приложения и не меняет доверие уже установленных клиентов.

`services/tauri_integration` строит endpoint и JSON из публичного адреса текущего запроса, постоянного slug и сохранённого ключа. Placeholders сохраняются, без ключа configuration=null. Готовность проверяет актуальные совместимые подписанные updater по платформам через общий resolver, inspect без хеширования либо validate по POST /readiness. Блокировки: отсутствие ключа/публикаций/подписанного updater, непубличное приложение, production HTTP, ошибки файлов.

Мастер вызывает существующий `TauriUpdater.preview` (теперь доступен оператору как чтение с session/CSRF), который использует прежние `select`/`response`. Preview содержит выбранную версию и имя файла; production endpoint и манифест обновлены вместе с моделью публикаций. Затем браузер проверяет настроенный публичный endpoint без cookie; DNS/TLS/proxy/CORS-ошибка не заменяется на отсутствие обновления. Сервер не делает внешних сетевых запросов. Готовность конфигурации, доступность HTTP и реальная установка клиента явно различаются; в БД нет статуса установки или телеметрии.

Переменные конфигурации используют имена разделов без префикса: `SERVER__BIND`, `DATABASE__PATH` и т. д.; TOML выбирается через `CONFIG`. Старые `VERUNA__…` и `VERUNA_CONFIG` отклоняются с инструкцией миграции. Из окружения читаются только известные разделы, опечатки внутри них отклоняются; посторонние переменные и их не-UTF-8 значения игнорируются.

Публикация фиксирует статус и факт первой публикации в одной транзакции. PublicDistribution получает согласованный каталог опубликованных релизов, сортирует SemVer и выбирает артефакт отдельно для target/типа/формата (без типа — прежний installer). Классификация использует существующий distribution_role: executable/installer/script/updater/archive; target задаёт платформу и при необходимости архитектуру. Latest и latest_by_type не подменяют разные типы. Tauri использует тот же каталог и выбирает совместимый подписанный updater. Переход старой схемы описан в [миграции 0009](migration-0009.md).

## Независимая идентичность standalone-продукта

`Application.product_id` задаётся издателем и отделён от внутреннего `id` и slug. `domain::standalone::verify` получает приложение целиком: проверяет внутреннюю принадлежность release/artifact, затем сопоставляет JWS v1 `application_id` с `product_id` и доверенным ключом. Upload, назначение подписи, публикационная валидация и StandaloneUpdater используют одну функцию без резервного сопоставления с внутренним UUID. Публикация сравнивает `product_id` вместе с ключом и остальным snapshot под write lock.

Настройки standalone доступны в существующей React-странице настроек приложения. UUID и публичный JWK сохраняются через прежний защищённый API; UI извлекает только публичное поле `x`, а сервер проверяет ключ и инварианты. GET через ApplicationCatalog и конкретный репозиторий читает настройки и флаги закрепления UUID/ключа в одном read snapshot. Проверка настроек в форме загрузки предварительная; загрузка по-прежнему проверяет текущие ключ, UUID, версию и подпись в write-транзакции. Настройки standalone обновляются атомарно через ApplicationCatalog, переданные и пропущенные поля различаются в HTTP DTO. BEGIN IMMEDIATE сериализует настройку с первой подписью и читает прежние значения после взятия блокировки, исключая потерю ключа при отдельном назначении идентичности. Миграция 0011 закрепляет прежние подписанные идентичности без изменения файлов/JWS. Постоянный флаг product_id_locked нужен, чтобы удаление черновика не позволяло повторно назначить уже использованную идентичность. Новых сервисов, реестров, протокольных полей или обязательной автоматизации нет; ручная неподписанная публикация остаётся исходным процессом.

## Самообновление процесса

Потребитель подписанных выпусков Veruna Releases подключён в точке запуска до открытия SQLite и HTTP. Адрес официального манифеста входит в настройки самообновления сервиса. Администратор может переопределить его в TOML или окружении. Клиент проверяет JWS выбранного исполняемого файла по встроенным UUID и публичному ключу Ed25519. Генератор manifest v2 добавляет `signed_metadata` для подписанных публичных `executable` после проверки по настройкам продукта. Публичный каталог обслуживает все продукты через прежний протокол standalone v1.

На Linux с фиксированным портом на loopback или wildcard сервис по умолчанию запускается в режиме `supervisor`. Каталог для рабочих копий и журнала по умолчанию расположен рядом с SQLite. Порт остаётся фиксированным при перезапуске для проверки готовности. Внешний режим использует `UpdateMonitor` по запросу администратора. На Linux `UpdateManager` владеет подготовкой файла, журналом, переключением и восстановлением. Встроенные миграции SQLx и метка формата файлов задают отпечаток совместимости. Административная команда повторно проверяет сессию и роль под `BEGIN IMMEDIATE` и держит блокировку до принятия операции. Длительная работа выполняется за пределами транзакции.

После завершения запросов и закрытия пула процесс подтверждает остановку. Готовность новой версии подтверждается чтением каталога приложений из SQLite и ответом на прямую loopback-пробу с идентификатором экземпляра. Публичный health endpoint сохраняет прежний контракт. Настройка, команды и восстановление описаны в [руководстве по самообновлению](self-update.md).
