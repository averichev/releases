# Standalone update protocol, версия 1

Это спецификация публичного HTTP-контракта для распространения отдельных исполняемых файлов. Она не требует SDK, определённого языка, реализации сервера, устройства приложения или менеджера процессов. Слова «обязан» и «отклоняется» задают требования совместимости. Примеры адресов и UUID условные.

## Граница ответственности и ручной процесс

Издатель предоставляет файл и подписанные метаданные. Сервер предоставляет метаданные и байты файла. Клиент независимо проверяет подпись и содержимое. Остановка процессов, замена установленного файла, запуск и восстановление после ошибок находятся за границей контракта.

Файл остаётся обычным HTTP-ресурсом для браузера, curl или wget. Один и тот же объект пригоден для первоначального получения и последующего обновления; отдельный установщик, агент или второй updater-пакет не требуются. Подпись необязательна для ручного распространения. Отсутствующая/некорректная подпись исключает доверенное автоматическое обновление, но сама по себе не запрещает скачать целый файл по обычной ссылке. Правила доступа сервера применяются к каждому запросу файла.

## Идентичность, версии и target

Издатель самостоятельно создаёт и сохраняет постоянный UUID продукта (`product_id`) один раз, до настройки серверов. Клиент заранее получает этот доверенный UUID, публичный Ed25519-ключ, базовый HTTPS URL сервера и собственную установленную SemVer-версию. `slug` служит для адресации на конкретном сервере. Внутренний `applications.id` принадлежит базе сервера и используется только для её связей и административных запросов.

В JWS v1 поле `application_id` содержит именно `product_id` издателя — канонический UUID со строчными hex-символами и дефисами (`8-4-4-4-12`). Название поля и `schema_version=1` сохраняются; второго поля идентичности нет. Один неизменённый бинарник и его JWS пригодны для независимых серверов с разными внутренними UUID и slug, если им явно назначены исходные `product_id` и публичный ключ. Идентичность не выводится из адреса, ключа или внутреннего UUID.

Для ранее выпущенных подписей «Релизы» при миграции закрепляют прежний внутренний UUID как `product_id` только у приложений с standalone-подписями, включая черновики. JWS и файлы остаются побайтно прежними. Этот UUID становится идентичностью издателя для дальнейших выпусков и переноса на другие серверы.

`target` имеет вид `<os>-<arch>` и обязан точно совпадать с объединением подписанных `os`, дефиса и `arch`:

| os | arch |
| --- | --- |
| windows | x86_64, aarch64 |
| linux | x86_64, aarch64 |
| darwin | x86_64, aarch64 |

Target описывает ABI исполняемого файла. Автоматического выбора другой ОС/архитектуры, alias, universal или musl/glibc fallback нет. Новые платформы могут вводиться отдельным совместимым расширением.

Версии сравниваются по [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html): build metadata сохраняется в идентичности подписанного выпуска, но не повышает precedence. Сервер выбирает самую новую опубликованную стабильную версию со standalone-подписью для точного target, строго новее установленной. Draft и prerelease не участвуют. Отсутствие подходящего подписанного файла в новом выпуске разрешает переход к предыдущему подходящему выпуску. Например, Windows 0.5.0 и macOS 0.6.0 дают независимые ответы 0.5.0 и 0.6.0. Обнаруженная нарушенная подпись/целостность назначенного кандидата блокирует обновление, а не вызывает скрытый откат к более старому файлу.

## Подписанный документ

Используется [JWS Compact, RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html) с [EdDSA/Ed25519, RFC 8037](https://www.rfc-editor.org/rfc/rfc8037.html). Это строка `BASE64URL(header).BASE64URL(payload).BASE64URL(signature)` без padding и переносов. Максимум — 4096 байт.

Защищённый header:

```json
{"alg":"EdDSA","typ":"releases-standalone+jws","kid":"JWK_THUMBPRINT"}
```

`alg` и `typ` обязательны с указанными значениями. `kid` необязателен для совместимости с первоначальными подписями; если присутствует, это строка с SHA-256 JWK thumbprint доверенного ключа. `null`, пустой/несовпадающий идентификатор и любые другие заголовки отклоняются. Не разрешены переключение алгоритма, `jwk`/`jku`, remote keys, `crit`, detached payload и `b64=false`.

Издатель включает `kid` явно, после проверки поддержки клиентами: клиент первоначального профиля мог отклонять неизвестные заголовки. Существующие подписи без `kid` сохраняют свои байты и проверяемость; сервер не добавляет идентификатор в чужой подписанный документ.

Payload — UTF-8 JSON-объект:

```json
{
  "schema_version": 1,
  "application_id": "e81a5470-8414-40a1-8596-71bf674f4568",
  "version": "0.5.0",
  "os": "windows",
  "arch": "x86_64",
  "size_bytes": 12345678,
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
```

Все семь полей обязательны. `schema_version` — целое 1; `application_id`, `version`, `os`, `arch`, `sha256` — строки; `size_bytes` — положительное целое, которое получатель обязан обрабатывать без потери точности. `version` — каноническая SemVer-строка, включая build metadata. `sha256` — ровно 64 строчных hex-символа. Неизвестные/повторяющиеся поля header и payload отклоняются.

Подпись проверяется над **исходными** ASCII-байтами `BASE64URL(header).BASE64URL(payload)`. JSON не пересобирается перед проверкой: порядок полей и допустимые пробелы не требуют согласования сериализаторов. Размер и SHA-256 относятся к байтам самого файла. UUID, версия, target, размер и хеш связывают подписанный документ с конкретным содержимым выпуска; транспортный URL может меняться без переподписания файла.

## Идентификатор ключа и расширение доверия

Ключ представляет публичный JWK `{"kty":"OKP","crv":"Ed25519","x":"…"}`. `x` — base64url без padding от 32 байт; приватное поле `d` не передаётся серверу или клиенту. Идентификатор определяется [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638.html):

```text
canonical = UTF8('{"crv":"Ed25519","kty":"OKP","x":"' + x + '"}')
kid = BASE64URL_NO_PADDING(SHA256(canonical))
```

Здесь `x` уже проверен как base64url, имена полей расположены лексикографически; другие поля JWK не включаются. Контрольный пример из RFC 8037 A.3: для `x=11qYAYKxCrfVS_7TyWQHOg7hcvPapiMlrwIaaPcHURo` получается `kid=kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k`. Это публичный тестовый ключ.

`kid` выбирает только среди ключей, которым клиент уже доверяет; он не является URL или разрешением доверять новому ключу. В нынешнем профиле доверенный ключ один, поэтому подпись без `kid` однозначна. При будущем расширении клиент сможет хранить набор доверенных ключей по thumbprint и принимать переход в рамках собственной явно определённой политики доверия. Для подписи без `kid` при нескольких ключах понадобится однозначно назначенный старый ключ либо отказ. Протокол сейчас не объявляет автоматическую ротацию/отзыв или способ доставки новых доверенных ключей; новый ключ из ответа сервера не принимается автоматически. Наличие `kid` позволяет расширить эту политику без смены схемы файла или значения уже существующих идентификаторов.

## Поиск обновления по HTTP

Базовый URL конфигурируется независимо от клиента. Запрос:

```http
GET /api/v1/updates/standalone/{slug}/{target}?current_version=0.4.0
Accept: application/json
```

`current_version` обязателен и URL-кодируется, в частности `+` в build metadata передаётся как `%2B`. Дополнительные/повторные query-параметры отклоняются. Сервер может для совместимости нормализовать префикс `v` и внешние пробелы входной версии; издатель подписывает каноническую версию.

Успешный ответ `200 application/json`:

```json
{
  "version": "0.5.0",
  "url": "https://downloads.example.test/files/immutable-artifact-id",
  "signed_metadata": "BASE64URL_HEADER.BASE64URL_PAYLOAD.BASE64URL_SIGNATURE"
}
```

`url` — абсолютный URL конкретного файла, который клиент трактует как непрозрачный HTTP-адрес. Его структура не является путём на локальном диске клиента. Подпись проверяется по `signed_metadata`; поле `version` обязано совпасть с подписанной версией. Сам URL не подписан: разрешённые origin и редиректы ограничиваются локальной политикой клиента. Нельзя передать серверу произвольный путь скачивания в запросе поиска.

Ответы поиска и ошибок имеют `Cache-Control: no-store`:

| Статус | Значение |
| --- | --- |
| 200 | Более новый подписанный файл найден; необходима независимая проверка клиентом. |
| 204 | Подходящего более нового подписанного файла нет; тело пустое. |
| 400 / 422 | Неверные параметры, SemVer или target. |
| 404 | Приложение не найдено или недоступно публично. |
| 503 | Обнаруженная ошибка подписи, состояния или целостности блокирует обновление; повторить позже/сообщить администратору. |

У ошибок JSON envelope вида `{"error":{"code":"standalone_unavailable","message":"…"}}`; `code` определяет причину, `message` предназначен для человека. Для хранилища может возвращаться `storage_unavailable` или `storage_busy`. Содержимое файла передаётся обычным GET; возможность HEAD/Range определяется HTTP-сервисом распространения и не меняет проверку окончательных байтов.

## Обязательная последовательность проверки клиентом

```text
Получить ответ поиска с ограничениями размера и времени.
Если 204: закончить; иначе требовать 200 и корректную структуру ответа.
Разобрать ограниченный JWS; проверить профиль header и схему payload.
Выбрать заранее доверенный ключ; при наличии kid сверить его thumbprint.
Проверить Ed25519-подпись над исходным JWS signing input.
Сверить application_id с доверенным product_id издателя, target — с ABI сборки.
Сверить version ответа с подписанной версией.
Сравнить подписанную версию с установленной: требовать строгое повышение SemVer.
Проверить политику origin/редиректов URL.
Скачать файл потоково во временный объект с лимитом подписанного размера.
Проверить точный размер и SHA-256 скачанных байтов.
Только после всех проверок считать файл доверенным; дальнейшие действия вне протокола.
```

Серверная проверка не заменяет ни подпись, ни хеш на клиенте. Приватный ключ хранится только у издателя. Сервер без него не может подделать новый документ, но может скрыть выпуск, задержать выдачу или сделать сервис недоступным. Проверка версии предотвращает downgrade относительно установленного файла, но не обеспечивает свежесть ещё не установленного выпуска. Сложная защита от freeze/rollback, TUF, отзыв ключей и гарантии доступности не входят в этот профиль.

Сервер проверяет полный хеш при приёме/публикации и явной проверке целостности; публичный GET не обязан повторно читать весь файл перед передачей. Подмена того же размера после публикации поэтому может не вызвать `503` при поиске. Клиент обнаруживает её по подписанному SHA-256 до использования файла.
