# Подписанные обновления standalone-приложений

Протокол распространяет один исполняемый файл на ОС/архитектуру. Этот же файл скачивают вручную и получают как обновление. Новые файлы используют роль `executable`; прежний `installer` сохраняет совместимость. Непустое поле `standalone_signature` явно назначает файл для автоматических обновлений. Копия файла и отдельный updater-пакет не нужны. Протокол не устанавливает файл, не перезапускает приложение и не управляет процессами.

Независимый от реализации сервера и языка клиента контракт: [Standalone update protocol, версия 1](standalone-protocol.md). Этот документ описывает его подключение к платформе. Node.js в примерах — необязательный инструмент издателя для проверки протокола; клиент может использовать любую стандартную JWS/Ed25519-библиотеку своего языка.

В панели сценарий «Пакет обновления» последовательно запрашивает ОС, архитектуру, бинарник и `.jws` из той же сборки. UUID продукта и публичный ключ предварительно настраиваются через административный API; отдельного мастера настройки ключа нет. Tauri Updater сохраняет собственные updater-пакеты, ключи и minisign `.sig`. Универсальный `manifest.json` остаётся schema_version=2 с прежними полями, `latest_by_target` для installer и `latest_by_type.executable` для executable. Отсутствие standalone-подписи ничего не меняет для старых публикаций и ручных скачиваний.

## Ручное распространение

Это основной путь получения файла. Опубликуйте обычный `executable` и передайте пользователю постоянную ссылку из каталога или manifest v2. Для него не нужны `product_id`, ключ и standalone-подпись. По этой ссылке работают браузер, curl и wget:

```sh
FILE_URL=https://apps.example.test/product/releases/0.5.0/artifacts/UUID_АРТЕФАКТА/download
curl --fail --output product.exe "$FILE_URL"
# Альтернатива:
wget --output-document=product.exe "$FILE_URL"
```

Для ручного обновления пользователь скачивает файл нужной платформы, останавливает предыдущий процесс, заменяет бинарник и запускает новую версию своим обычным способом. Платформа предоставляет файл и метаданные; способ запуска ей неизвестен. На Unix пользователь сохраняет executable permission. Дополнительные библиотеки, агенты и отдельный установщик не требуются. Public/private и active/archived проверяются прежними механизмами; приватные файлы остаются доступны через защищённые административные скачивания, публичные ссылки для них возвращают 404.

Чтобы распространять только вручную, не передавайте `standalone_signature`. Подписанный файл сохраняет свои роль, ID и URL. Автоматический endpoint может выбрать более старый подписанный файл, в то время как ручной `/latest?type=executable` продолжает указывать на более новый неподписанный executable. Ссылки без type сохраняют выбор installer.

## Подпись и доверие

Схема подписанных полей, исходные байты JWS и алгоритм независимой проверки определены в [спецификации](standalone-protocol.md#подписанный-документ). Платформа проверяет их через `jsonwebtoken` 12 с RustCrypto, совместимый с Rust 1.91. Подпись связывает постоянный UUID продукта издателя (`product_id` в настройках, `application_id` в JWS v1), точную версию, ОС/архитектуру, размер и SHA-256 с одним существующим артефактом. Идентификатор артефакта не требуется получать до подписи: соответствие задают поля выпуска/платформы, проверенный хеш и ограничение единственного standalone на release/target.

Необязательный защищённый `kid` — стандартный SHA-256 JWK thumbprint. При наличии он обязан совпадать с доверенным ключом приложения. Старые JWS без `kid` остаются корректными. Идентификатор вычисляется библиотекой и не требует нового столбца, таблицы или реестра ключей.

Пример `sign` по умолчанию сохраняет прежний header без `kid`. Флаг `--kid` в конце команды явно включает идентификатор; используйте его после проверки поддержки клиентами. Пример `verify` принимает оба варианта. Сервер не дописывает `kid` к уже существующим подписям и не переподписывает их.

Приватный ключ остаётся на машине подписания/в защищённом CI, никогда не передаётся «Релизам». Для каждого приложения нужна отдельная пара. На сервер сохраняется только Ed25519 JWK `x`: base64url без padding, 32 байта / 43 символа. Приватные ключи и Tauri envelope не принимаются. Повторное использование одного ключа другим приложением запрещено индексом БД.

После привязки хотя бы одного подписанного артефакта ключ нельзя заменить/удалить (`409`). Для черновиков можно сначала снять назначения или удалить файлы. В текущей реализации опубликованные файлы закрепляют ключ: его смена без сохранения доверия старым выпускам была бы небезопасной. Опциональный `kid` оставляет возможность будущего набора доверенных ключей; сама ротация потребует отдельно определённой политики клиента и нового расширения хранения, без изменения уже применённой миграции или переподписания старых JWS. Клиент должен получить ключ и `product_id` независимо от сервера, например при сборке. Ключ, полученный вместе с ответом обновления, не является доверенным.

## Подготовка и загрузка

Рабочий пример без npm-зависимостей: [example.mjs](standalone/example.mjs), Node.js 22+. Он только подписывает и проверяет локальные файлы. На машине подписания создайте пару вне репозитория:

```sh
node docs/integrations/standalone/example.mjs keygen /secure/product-signing
```

Команда создаёт `/secure/product-signing.pem` (приватный, режим 0600; на Windows дополнительно настройте ACL) и `/secure/product-signing.public.jwk`. stdout содержит JSON `{"public_key":"…"}` для сохранения в API. Защитите ключ и его резервную копию; пример хранит PEM без пароля и не заменяет secret manager.

Издатель один раз создаёт UUID продукта любым локальным инструментом и сохраняет вместе с исходным кодом/конфигурацией сборки. Например, `node -e 'console.log(require("node:crypto").randomUUID())'`. Сервер его не генерирует. Значение ниже — пример; подставьте собственное. Подпишите **окончательные байты** файла после сборки и любых операций OS code signing, ещё до создания приложения на сервере:

```sh
PRODUCT_ID=e81a5470-8414-40a1-8596-71bf674f4568
node docs/integrations/standalone/example.mjs sign /secure/product-signing.pem "$PRODUCT_ID" 0.5.0 windows-x86_64 ./build/windows/product.exe > ./build/windows/product.jws
node docs/integrations/standalone/example.mjs sign /secure/product-signing.pem "$PRODUCT_ID" 0.5.0 darwin-aarch64 ./build/macos/product > ./build/macos/product.jws
node docs/integrations/standalone/example.mjs sign /secure/product-signing.pem "$PRODUCT_ID" 0.5.0 linux-x86_64 ./build/linux/product > ./build/linux/product.jws
```

Административные запросы используют действующую сессию администратора, `Origin`, `X-Veruna-Request: 1` и `X-CSRF-Token`. Ниже `session.cookies` — локальный cookie jar из входа, `CSRF` — токен ответа `/api/v1/auth/me`. Не сохраняйте эти файлы в Git. Создайте Application и черновик Release через панель или [admin API](../admin-api.md). `APP` содержит внутренний UUID записи, полученный от этого сервера, и не используется при подписании:

```sh
BASE=https://apps.example.test
APP=UUID_ЗАПИСИ_НА_ЭТОМ_СЕРВЕРЕ
RELEASE=UUID_СОЗДАННОГО_РЕЛИЗА
# public-key.json — JSON из stdout keygen, без приватного ключа.
node --input-type=module -e 'import fs from "node:fs"; const key=JSON.parse(fs.readFileSync("public-key.json")); console.log(JSON.stringify({...key,product_id:process.argv[1]}));' "$PRODUCT_ID" > standalone-settings.json
curl --fail-with-body -X PUT "$BASE/api/v1/admin/applications/$APP/integrations/standalone" \
  -b session.cookies -H "Origin: $BASE" -H 'X-Veruna-Request: 1' \
  -H "X-CSRF-Token: $CSRF" -H 'Content-Type: application/json' --data-binary @standalone-settings.json
```

`GET` того же endpoint доступен operator/admin и возвращает `application_id` (внутренний UUID), `product_id` (UUID издателя), `public_key` и вычисленный `key_id` (либо null без ключа). PUT меняет только переданные поля: `{"product_id":"UUID"}` сохраняет ключ, `{"public_key":"…"}` сохраняет идентичность; оба можно задать атомарно. `null` явно очищает соответствующее ещё не закреплённое значение. Неканонический UUID — 422, занятый или закреплённый `product_id` — 409 `standalone_product_conflict`. На одном сервере UUID уникален, включая архивные приложения; на независимых серверах повторяется свободно.

Перед первой подписью явно задайте `product_id` и ключ. С момента сохранения первой подписи, в том числе в черновике, `product_id` закрепляется навсегда в сервисе и SQLite. Снятие подписи или удаление черновика не снимает закрепление. При обновлении существующей базы миграция `0011` назначает прежний внутренний UUID приложения как `product_id` при наличии любой standalone-подписи; иначе оставляет null, даже если уже настроен ключ. Она не меняет UUID записей, JWS, бинарники или другие данные выпусков. Для старого подписанного продукта используйте именно закреплённый UUID в следующих сборках и на других серверах.

Загрузка одного файла (повторите для двух остальных с соответствующим `target`, `file_type=bin`):

```sh
curl --fail-with-body "$BASE/api/v1/admin/applications/$APP/releases/$RELEASE/artifacts" \
  -b session.cookies -H "Origin: $BASE" -H 'X-Veruna-Request: 1' -H "X-CSRF-Token: $CSRF" \
  -F target=windows-x86_64 -F distribution_role=executable -F file_type=exe \
  -F file=@./build/windows/product.exe -F standalone_signature=@./build/windows/product.jws
```

`target`, `file_type`, `distribution_role` должны идти до `file`. Файл `.jws` может идти до или после него. `standalone_signature` обязательно передаётся как файл с расширением `.jws`, Tauri `signature` по-прежнему принимает `.sig`. Сервер потоково вычисляет размер/SHA-256, проверяет JWS текущим ключом и версией в транзакции, затем фиксирует единственную запись артефакта. Некорректный JWS не оставляет доступного файла/записи.

В черновике можно назначить уже загруженный installer без повторной загрузки:

```text
PUT /api/v1/admin/applications/{id}/releases/{release}/artifacts/{artifact}/standalone
Content-Type: application/json
{"signed_metadata":"eyJ…полный compact JWS…"}
```

`{"signed_metadata":null}` снимает назначение в черновике. Подпись проверяется сразу; при публикации повторно проверяются подпись, связанные поля и полный SHA-256. Смена версии черновика требует нового подписания. Публикация сравнивает проверенный snapshot с текущими данными под write lock, включая `product_id`, ключ и подписи. Ошибка транзакции не оставляет частично опубликованный релиз. После публикации существующие файлы и подписи неизменяемы. Дополнение опубликованного релиза другой платформой разрешено тем же multipart API; JWS должен передаваться в одной загрузке. Не требуется отдельного релиза или канала.

## Перенос на независимый сервер

На сервере B создайте приложение с его собственными UUID и slug. Тем же PUT назначьте **исходные** `product_id` и `public_key`, создайте релиз той же версии, загрузите те же файлы и `.jws`, затем опубликуйте. Внутренние UUID приложений/релизов/артефактов могут отличаться. Базы, конфигурация серверов, приватный ключ, повторная сборка и переподписание для переноса не нужны. Для клиента меняется разрешённый HTTPS endpoint по его локальной политике; доверенные `product_id` и ключ сохраняются. Другой совместимый сервер может предоставлять иной административный процесс, сохраняя тот же публичный HTTP/JWS-контракт.

## Поиск обновления

```http
GET /api/v1/updates/standalone/product/windows-x86_64?current_version=0.4.0
```

```json
{
  "version": "0.5.0",
  "url": "https://apps.example.test/product/releases/0.5.0/artifacts/UUID_АРТЕФАКТА/download",
  "signed_metadata": "BASE64URL_HEADER.BASE64URL_PAYLOAD.BASE64URL_SIGNATURE"
}
```

Здесь сокращён только пример JWS; реальный ответ содержит исходную проверяемую строку. `url` строит сервер из разрешённого origin и постоянного ID артефакта. Адреса/пути клиента не принимаются. Успешные и ошибочные ответы имеют `Cache-Control: no-store`. GET/HEAD и CORS соответствуют публичному API; перед скачиванием снова проверяются публичность приложения, опубликованность и принадлежность файла. Работают существующие direct/Nginx delivery, Range и HEAD.

Платформы: `windows-x86_64`, `windows-aarch64`, `linux-x86_64`, `linux-aarch64`, `darwin-x86_64`, `darwin-aarch64`. Для `executable` расширение не ограничивает участие в обновлениях: допустимы обычный EXE, файл без расширения, `.x86_64`, `.tool` и другие имена. Например, `product-0.7.0-linux-x86_64` получает формат bin: окончание платформы не является расширением после точки версии. Для прежнего `installer` сохраняются exe на Windows и bin на Linux/macOS. Архитектура означает исполняемый ABI приложения, а не только физический CPU. Здесь нет автоматического Rosetta/universal/musl/glibc fallback; такие различия требуют отдельного будущего расширения контракта. `any`, `darwin-universal` и alias `macos-arm64` отклоняются. Исполняемость/Mach-O/PE/ELF не определяется по содержимому: издатель отвечает за правильный файл и ABI.

Используется единый каталог PublicDistribution, сортируемый по SemVer. Выбирается самый новый **подписанный standalone** для точной платформы, строго новее `current_version`. Draft и prerelease не участвуют. Например, Windows 0.5.0 и macOS 0.6.0 дают Windows 0.5.0 / macOS 0.6.0. Отсутствие Windows в 0.6.0 не блокирует предыдущую Windows-версию. Неподписанные executable/installer и Tauri updater пропускаются. Назначенный, но повреждённый кандидат блокирует выдачу (`503`), без отката к более старому файлу. Равная/старшая установленная версия даёт `204`. Build metadata не повышает SemVer precedence. Общий parser, как и существующее API, допускает префикс `v` и внешние пробелы в `current_version`; подписанная версия должна быть канонической.

| Код | Значение / действие |
| --- | --- |
| 200 | Есть подписанное обновление; клиент обязан независимо проверить JWS и содержимое. |
| 204 | Нет более новой совместимой подписанной версии; пустое тело. |
| 400 | Нет `current_version`, лишние/повторные query-параметры, некорректный запрос. |
| 422 | Неверный SemVer/target; в admin API также неверный ключ, JWS или несовпадение подписанных полей. |
| 404 | Slug не найден, приложение private или archived. |
| 503 `standalone_unavailable` | Назначенная подпись/метаданные недействительны или выбор неоднозначен; требуется ремонт администратором. |
| 503 `storage_unavailable` | Файл отсутствует, symlink/не regular file или размер изменён. |
| 503 `storage_busy` | Исчерпан лимит операций хранилища; повторить позже. |
| 409 (admin) | Конфликт артефакта, занятого/закреплённого `product_id` или ключа, попытка изменить опубликованный файл либо устаревшая ревизия публикации. |
| 422 `publication_blocked` (admin) | Публикация не прошла проверки, включая полный SHA-256/JWS. |

## Сквозная независимая проверка

Запросите обновление и сохраните ответ в `update.json` (`curl --fail-with-body ... -o update.json`; для `204` JSON отсутствует). Скопируйте `url` и `signed_metadata` в локальные файлы. Следующий пример проверяет один уже выбранный ответ без установки:

```sh
curl --fail-with-body "$BASE/api/v1/updates/standalone/product/windows-x86_64?current_version=0.4.0" -o update.json
node --input-type=module -e 'import fs from "node:fs"; const u=JSON.parse(fs.readFileSync("update.json")); fs.writeFileSync("candidate.jws",u.signed_metadata);'
# Используйте URL из ответа только после проверки HTTPS и разрешённого origin.
curl --fail-with-body 'URL_ИЗ_ОТВЕТА' -o candidate.exe
node docs/integrations/standalone/example.mjs verify /secure/product-signing.public.jwk "$PRODUCT_ID" 0.5.0 windows-x86_64 candidate.exe candidate.jws
```

Версия `0.5.0` здесь ожидаемая, а не автоматически доверенная из JSON. Пример потоково проверяет Ed25519/JWS, UUID, версию, платформу, размер и SHA-256; любое изменение приводит к ненулевому exit code. Эти операции можно выполнить без сети. Сам `update.json`, URL и неподписанные поля ответа не являются доказательством подлинности.

## Требования к любому клиенту

Клиент хранит встроенные `product_id` издателя, публичный ключ и собственную SemVer-версию. Он определяет канонический target по ABI текущей сборки и использует фиксированный HTTPS endpoint. Проверяет тип/размер ответа, фиксированные `alg`/`typ`, схему и все поля JWS, затем сравнивает подписанную версию с установленной по SemVer без downgrade. Поле `version` ответа должно совпасть с подписанным. Не загружает ключ из JWS или ответа, не принимает произвольный путь установки и не следует редиректам за пределы доверенного origin без отдельной политики.

Файл загружается потоково во временный объект с лимитом подписанного размера, таймаутами и вычислением SHA-256. До любого использования/замены файла клиент обязан сверить размер и хеш. На Unix потребуется корректно выставить executable permission; сервер распространяет байты, а не права файла. Установка, управление процессами и восстановление установленного приложения полностью находятся за границей ответственности платформы. Нормативный алгоритм проверки доступен в [спецификации](standalone-protocol.md#обязательная-последовательность-проверки-клиентом); импорт серверных модулей или привязка к конкретному продукту не нужны.

## Ограничения защиты

Подпись подтверждает происхождение и целостность связанных байтов, но не безопасность исполняемого кода. Компрометация приватного ключа позволяет выпускать вредоносные подписанные обновления. Компрометация сервера без ключа позволяет скрывать обновления, задерживать их или отдавать старые подписанные версии; сравнение с установленной версией предотвращает downgrade, но не freeze/rollback относительно ещё не установленного более нового выпуска. Нет TUF timestamp/snapshot/expiry, отзыва/ротации ключей, гарантии свежести и защиты от недоступности сети.

SHA-256 целиком вычисляется при загрузке, публикации и явной admin-проверке. Публичные запросы проверяют ключ хранилища, regular-file/no-symlink и размер; не перечитывают гигабайты на каждый GET. Поэтому подмена **того же размера после публикации** обнаруживается клиентом при сверке подписанного SHA-256 либо явной проверкой/повторной публикационной валидацией, но не гарантирует `503` при поиске обновлений. Явная проверка сообщает результат, не меняя неизменяемый артефакт. Защита диска и корректный internal Nginx alias остаются обязательными условиями эксплуатации.
