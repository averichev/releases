# Tauri 2 Updater и Veruna Releases

Интеграция находится в **Приложения → нужное приложение → Интеграции → Tauri Updater**:
`/admin/applications/:applicationId/integrations/tauri`.
Это инструкция по подключению клиентского проекта к существующему серверу обновлений. Сервер не модифицирует исходники приложения.

Мастер получает имя, постоянный slug, публичный адрес текущего HTTPS-домена (или явного `download.public_base_url`), сохранённый публичный ключ, актуальные версии updater по платформам, updater-пакеты и результаты проверки публикации. Пакетный менеджер, и шаг сохраняются в query-параметрах страницы, поэтому перезагрузка и возврат сохраняют выбранный шаг. Оператор может читать инструкцию и выполнять диагностику; сохранение ключа требует администратора, действующей сессии и CSRF.

Источники API: [Tauri Updater](https://v2.tauri.app/plugin/updater/), [JavaScript API](https://v2.tauri.app/reference/javascript/updater/), [Rust UpdaterBuilder](https://docs.rs/tauri-plugin-updater/latest/tauri_plugin_updater/struct.UpdaterBuilder.html), [Process](https://v2.tauri.app/plugin/process/), [конфигурация Tauri](https://v2.tauri.app/reference/config/).

## 1. Установите плагины в клиентское приложение

Из корня существующего Tauri 2 проекта с установленным CLI:

| Менеджер | Updater | Перезапуск из JavaScript |
| --- | --- | --- |
| npm | `npm run tauri add updater` | `npm run tauri add process` |
| pnpm | `pnpm tauri add updater` | `pnpm tauri add process` |
| yarn | `yarn tauri add updater` | `yarn tauri add process` |
| bun | `bunx tauri add updater` | `bunx tauri add process` |

Проверьте зависимости Rust (`tauri-plugin-updater`, `tauri-plugin-process`) и JS (`@tauri-apps/plugin-updater`, `@tauri-apps/plugin-process`). В `src-tauri/src/lib.rs` дополните **существующий** `.setup(|app| { ... })` в Tauri Builder:

```rust
#[cfg(desktop)]
{
    app.handle().plugin(tauri_plugin_updater::Builder::new().build())?;
    app.handle().plugin(tauri_plugin_process::init())?;
}
```

Оставьте остальной setup и завершающий `Ok(())`. Если setup отсутствует, добавьте `.setup(|app| { /* строки выше */ Ok(()) })` перед `.run(...)`. Не заменяйте весь `lib.rs` и не регистрируйте один плагин дважды. Сохраните свои команды и другие плагины.

В массив `permissions` существующего capability локального окна (обычно `src-tauri/capabilities/default.json`) добавьте:

```json
{
  "permissions": ["updater:default", "process:allow-restart"]
}
```

Это дополнение: сохраните `identifier`, `windows`, остальные разрешения. Не выдавайте команды обновления недоверенному удалённому содержимому.

**Проверка:** клиент собирается, capability относится к используемому окну, вызовы updater/process разрешены.

## 2. Создайте и сохраните пару ключей

Рекомендуется отдельная пара для каждого независимого приложения. Пример для slug `videolov`:

```sh
mkdir -p ~/.tauri
pnpm tauri signer generate -w ~/.tauri/videolov.key
```

Для npm: `npm run tauri signer generate -- -w ~/.tauri/videolov.key`; yarn: `yarn tauri signer generate -w ~/.tauri/videolov.key`; bun: `bunx tauri signer generate -w ~/.tauri/videolov.key`. В PowerShell создайте каталог через `New-Item -ItemType Directory -Force ~/.tauri`. При необходимости укажите полный путь домашнего каталога вашей оболочки.

- **`videolov.key` — приватный ключ.** Нужен только машине сборки. Храните его и пароль в защищённом месте с резервной копией. Не отправляйте Veruna и не добавляйте в Git. Потеря ключа мешает обновлению клиентов, уже доверяющих ему.
- **`videolov.key.pub` — публичный ключ.** Содержимое встраивается в клиент; его можно хранить на сервере. Скопируйте полное base64-содержимое файла в поле шага 2 и сохраните.

API принимает только публичный Tauri/minisign envelope с публичным пакетом. Файловые пути, приватные ключи, подписи вместо ключей и поля пароля отклоняются. Публичный ключ хранится в SQLite как настройка приложения, а не в системе секретов.

**Проверка:** после сохранения шаг 3 содержит именно ваш ключ. Без ключа мастер показывает предупреждение и не выдаёт фиктивную готовую конфигурацию. Смена ключа на сервере меняет только генерируемую инструкцию; установленный клиент продолжает использовать встроенный ключ. Для ротации нужна заранее реализованная клиентская логика.

## 3. Дополните tauri.conf.json

Готовый JSON формируется на backend одним генератором, с безопасной сериализацией и адресом из конфигурации сервера. Документ ниже — статический пример для VideoLov; значение ключа обозначено явно и не является рабочим ключом:

```json
{
  "bundle": { "createUpdaterArtifacts": true },
  "plugins": {
    "updater": {
      "pubkey": "ВСТАВЬТЕ_СОДЕРЖИМОЕ_СВОЕГО_.key.pub",
      "endpoints": [
        "https://apps.veruna.systems/api/v1/updates/tauri/videolov/{{target}}/{{arch}}/{{current_version}}"
      ]
    }
  }
}
```

Объедините фрагмент с `src-tauri/tauri.conf.json`, сохранив `identifier`, `version`, `productName`, параметры bundler и других плагинов. Не заменяйте весь файл.

`{{target}}`, `{{arch}}`, `{{current_version}}` заполняет клиент Tauri. Оставьте их как есть. Для macOS target — `darwin`; для Windows/Linux — `windows`/`linux`. Production требует HTTPS. По умолчанию адрес использует домен панели, HTTPS подтверждается локальным proxy. Явный `download.public_base_url` фиксирует отдельный домен; Forwarded игнорируется.


**Проверка:** JSON корректен, ключ не является путём к файлу, адрес и slug соответствуют приложению, переменные Tauri сохранены.

## 4. Подключите проверку, загрузку и установку

Готовая функция: **[client.ts](tauri/client.ts)**. Скопируйте файл в свой клиентский проект. Этот же файл без дублирования импортируется как текст в веб-мастер. Функция:

1. Вызывает `check()` с таймаутом.
2. Сообщает об отсутствии обновления либо показывает доступную и установленную версии.
3. Запрашивает согласие пользователя.
4. Загружает и устанавливает пакет через `downloadAndInstall`, показывает проценты или число байт при неизвестном размере.
5. Показывает ошибки, освобождает неустановленный Update и предотвращает параллельные вызовы.
6. Вызывает `relaunch()` после установки, когда процесс продолжает работу.

Пример обычной HTML-кнопки без привязки к React или конкретному продукту: **[button.ts](tauri/button.ts)**. В HTML нужны `#check-updates` и `#update-status`; подключайте скрипт после появления элементов. Перед установкой предложите пользователю сохранить незавершённую работу.

На **Windows** updater запускает установщик и завершает текущий процесс: последующий JS может не выполниться, дальнейший запуск зависит от установщика. На **Linux/macOS** нужен перезапуск для запуска новой версии. Проверяйте эти сценарии на каждой целевой ОС.

Ручная проверка: действие «Настройки → Проверить обновления» вызывает эту функцию. Автоматическая проверка: вызов после инициализации интерфейса либо с разумной периодичностью. Эта функция всё равно спрашивает согласие. Для фоновой проверки без диалога используйте отдельно `check()`, сообщите о версии и вызовите `update.close()`, если установка отложена. Не устанавливайте обновления без уведомления и не запускайте параллельные проверки.


## 5. Соберите подписанный пакет

В Bash/zsh задайте переменные только для процесса сборки:

```sh
export TAURI_SIGNING_PRIVATE_KEY="$HOME/.tauri/videolov.key"
printf 'Пароль ключа: '
IFS= read -r -s TAURI_SIGNING_PRIVATE_KEY_PASSWORD
printf '\n'
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD
pnpm tauri build
unset TAURI_SIGNING_PRIVATE_KEY TAURI_SIGNING_PRIVATE_KEY_PASSWORD
```

Для ключа без пароля введите пустую строку. В PowerShell:

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = "$HOME/.tauri/videolov.key"
$secret = Read-Host "Пароль ключа" -AsSecureString
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = [System.Net.NetworkCredential]::new("", $secret).Password
try { pnpm tauri build }
finally {
  Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY
  Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD
}
```

Для других менеджеров используйте соответствующую команду `npm run tauri build`, `yarn tauri build`, `bunx tauri build`. В CI храните ключ и пароль в защищённом окружении; настройки CI/CD не входят в эту интеграцию. Tauri не читает эти переменные из `.env` автоматически. Не храните ключ в исходниках и не загружайте его как релиз.

При `bundle.createUpdaterArtifacts = true` типичные результаты в `target/release/bundle`:

| ОС | Updater-пакет и подпись | Target/format Veruna |
| --- | --- | --- |
| Windows | NSIS `*.exe` или `*.msi`, соответствующая `.sig` | windows-x86_64/aarch64; exe/msi |
| Linux | `*.AppImage`, `*.AppImage.sig` | linux-x86_64/aarch64; appimage |
| macOS | `*.app.tar.gz`, `*.app.tar.gz.sig` | darwin-x86_64/aarch64/universal; tar.gz |

Имена и типы зависят от версии Tauri и bundler. DMG, DEB/RPM и произвольный EXE не гарантируют updater-совместимость. Для macOS ручной DMG можно хранить отдельно с назначением installer. Режим `v1Compatible` для старого Tauri этим адаптером не поддерживается.

Подпись Tauri Updater отличается от code signing Windows/macOS и notarization: они решают отдельные задачи и настраиваются отдельно.

**Проверка:** есть нужный updater-пакет и его `.sig`; версия совпадает с SemVer будущего релиза; секретов нет в репозитории/дистрибутиве.

## 6. Загрузите и опубликуйте релиз

1. Откройте приложение → **Релизы** → создайте релиз.
2. Укажите SemVer той же версии, что встроена в Tauri-клиент, и описание изменений.
3. Нажмите **Добавить артефакт**, выберите **Пакет обновления Tauri**, затем ОС и архитектуру сборки. В списке показан точный target, например `windows-x86_64`; x86_64 не означает Universal.
4. Выберите updater-пакет.
5. Прикрепите соответствующий `.sig` (до 16 КиБ) в той же форме. Оба файла обязательны и для черновика. API позволяет добавить подпись к черновику отдельно.
6. Повторите для остальных поддерживаемых платформ.
7. Выполните существующую проверку готовности публикации.
8. Исправьте ошибки и предупреждения подписи.
9. Опубликуйте релиз. Сервер автоматически выберет последнюю совместимую версию для каждой платформы.
10. Вернитесь в интеграцию, обновите данные и выполните диагностику.

Уже опубликованную версию можно дополнить новым updater без создания второго релиза. В этом случае `.sig` обязательна в той же операции загрузки, файл после сохранения неизменяем. Для платформы допускается один updater независимо от формата; installer с теми же target/format хранится отдельно. Первая дата публикации сохраняется.

Мастер показывает, есть ли опубликованные релизы и подходящие подписанные пакеты, список updater-файлов, платформы, совместимость формата и наличие корректно оформленной подписи. **Это не криптографическая проверка пары пакет/ключ.** Её выполняет установленный Tauri-клиент. SHA-256 также не является цифровой подписью.

Страница проверяет наличие/размер безопасно открытого файла без полного перечитывания. Кнопка **«Проверить готовность и SHA-256 файлов»** явно запускает существующий PublicationValidator с полным хешированием. Опубликованные пакеты и подписи неизменяемы: исправление требует нового релиза.

## 7. Проверьте сервер и реальную установку

### Серверный протокол

На шаге 7 выберите ОС, архитектуру и текущую версию клиента, затем **«Проверить обновление»**. Существующий административный preview вызывает общий механизм выбора; отдельного алгоритма версий нет.

Результат содержит установленную версию, выбранную версию для платформы, выбранный файл, наличие подписи, постоянный URL, реальный JSON Tauri и причину выбора. Затем браузер запрашивает публичный endpoint без административной сессии. Другой origin может требовать CORS; ошибка DNS/TLS/proxy/CORS показывается как недоступность проверки, не как отсутствие обновления. Сервер не выполняет произвольные внешние запросы.

Например:

```sh
curl -i 'https://apps.veruna.systems/api/v1/updates/tauri/videolov/windows/x86_64/1.0.0'
```

Контракт сохранён: `200` с `version/pub_date/url/signature/notes`; `204` без тела при отсутствии публикаций, версии не новее или отсутствии пакета для валидной платформы. Preview различает эти причины. Private/archived/несуществующее приложение — `404`; невалидная версия/target — `422`; неверная подпись или неоднозначный пакет — `503 updater_unavailable`; отсутствующий/повреждённый по размеру файл — `503 storage_unavailable`. Ошибки не маскируются под `204`.

Tauri-протокол распознаёт x86_64/aarch64/i686/armv7; каталог загрузок принимает пакеты x86_64/aarch64 и `darwin-universal` для macOS Intel + Apple Silicon. Для macOS клиент по-прежнему передаёт свою архитектуру: сервер предпочитает точный пакет, а при его отсутствии выбирает Universal. Для валидной, но не представленной платформы preview объяснит отсутствие пакета. Updater выбирает максимальную опубликованную SemVer с совместимым подписанным пакетом. Prerelease исключены. Более новый installer-only релиз не скрывает предыдущий updater. Версия, равная или меньшая версии клиента, не предлагается.

### Реальная установка: 1.0.0 → 1.0.1

1. Соберите и установите клиент **1.0.0** с Updater, endpoint и публичным ключом.
2. Соберите **1.0.1**, подписав тем же приватным ключом.
3. Загрузите пакет в релиз 1.0.1 Veruna Releases.
4. Прикрепите соответствующий `.sig`.
5. Проверьте и опубликуйте 1.0.1.
6. Запустите установленную 1.0.0.
7. Выполните проверку обновлений.
8. Убедитесь, что обнаружена 1.0.1.
9. Подтвердите загрузку и установку.
10. После перезапуска проверьте фактическую версию 1.0.1 и отсутствие повторного предложения обновиться.

Повторите на каждой поддерживаемой ОС. Серверная диагностика не доказывает, что клиент проверил подпись, установил пакет и перезапустился. Никакой фиктивный статус успешной установки в БД не сохраняется.

**Клиенты, выпущенные без Tauri Updater, не могут получить его автоматически.** Пользователь должен вручную установить первую сборку с интеграцией.

## Статусы и административный API

Блокирующие состояния: нет публичного ключа; нет опубликованного релиза; отсутствует совместимый подписанный updater-пакет; приложение недоступно публично; HTTP вместо production HTTPS; ошибки существующей проверки публикации/файлов. Статус **«Серверная конфигурация готова»** означает выполнение этих серверных условий для представленных платформ на момент запроса. Внешнюю доступность проверяет отдельный публичный запрос браузера. Реальная установка остаётся отдельным тестом.

- `GET /api/v1/admin/applications/{id}/integrations/tauri` — ключ, endpoint, фрагмент JSON, актуальные пакеты и готовность без полного SHA-256.
- `PUT /api/v1/admin/applications/{id}/integrations/tauri` — `{ "public_key": "содержимое .key.pub" }`; `null` очищает ключ; успех `204`. Только admin, session + CSRF, повторная авторизация внутри write-транзакции. Неизвестные поля запрещены.
- `POST /api/v1/admin/applications/{id}/integrations/tauri/readiness` — явная проверка с полным SHA-256, те же данные готовности. Session + CSRF; доступна оператору.
- Существующий `POST /api/v1/admin/applications/{id}/updater/tauri/preview` с `{ "target": "windows-x86_64", "current_version": "1.0.0" }` — preview того же протокола, session + CSRF; доступен оператору, поскольку не изменяет данные.

Публичный endpoint `/api/v1/updates/tauri/{slug}/{target}/{arch}/{currentVersion}` выбирает подписанный updater по платформе. Не добавлены другие updater-протоколы, серверное подписание, private updates, CI/CD, телеметрия, принудительная установка или downgrade. Приложение остаётся одним Rust-бинарником со встроенным frontend.
