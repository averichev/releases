# Релизы и хранение дистрибутивов (этапы 4–6)

## Работа в панели

1. Войдите администратором, откройте **Приложения → нужное приложение → Релизы**.
2. Нажмите **Создать релиз**, введите `1.2.0`, необязательное название и описание. После сохранения откроется `/admin/applications/:applicationId/releases/:releaseId`.
3. Нажмите **Добавить артефакт**, выберите назначение (по умолчанию установщик), платформу и файл. Для Tauri Updater можно сразу приложить `.sig`. Следующие файлы добавляются последовательно; например, EXE для Windows x64 и TAR.GZ для Linux x64.
4. Дождитесь ответа сервера после передачи 100%. Таблица покажет фактические размер и SHA-256. Проверьте скачивание, копирование хеша и **Проверить SHA-256**.
5. Проверьте готовность и опубликуйте. При необходимости добавьте новые артефакты той же версии через ту же кнопку; updater в published требует `.sig` в этой форме. Существующие опубликованные файлы нельзя менять/удалять. У черновика удаление и изменение роли/подписи остаются доступны. Обновите вложенную страницу: она должна открыться снова.

Operator видит релизы и скачивает файлы, но не меняет данные. Новый релиз нельзя создать для архивного приложения; уже существующими черновиками можно управлять. Публикация, манифесты и подписи добавлены на этапе 5: см. [release-management.md](release-management.md). Публичные скачивания реализованы: [публичное распространение](public-distribution.md). API-токены отсутствуют.

## Данные и инварианты

Миграция `0004_releases_artifacts.sql` добавляет `releases` и `artifacts`. Связи используют UUID. UUID релиза, его приложение и created_at неизменяемы. Базовые поля Artifact неизменны; только в draft файл можно удалить и загрузить снова. Удаление черновика каскадно удаляет строки artifacts. Файловая система в каскад SQLite не входит.

Новый релиз — `draft`, published_at=NULL. PATCH меняет версию, title и release_notes только у draft. На этапе 5 миграция 0005 добавляет `published`: после явной публикации метаданные релиза и существующие артефакты/подписи неизменяемы. Миграция 0008 разрешает добавление новых файлов с увеличением revision, сохраняя published_at. Подробнее: [модель данных](data-model.md).

Версию проверяет `semver`: trim и один lowercase `v` в начале нормализуются. `version` сохраняет build metadata, но UNIQUE(application_id, version_key) использует SemVer без `+build`. Поэтому `1.2.0`, `v1.2.0` и `1.2.0+build.15` конфликтуют внутри одного приложения. В разных приложениях одинаковые версии допустимы. Это сознательно исключает два релиза с одинаковым приоритетом перед добавлением выбора актуального релиза. Сортировка использует [Version::cmp_precedence](https://docs.rs/semver/1.0.28/semver/struct.Version.html#method.cmp_precedence), а не текстовое сравнение или Ord, учитывающий build metadata. Поиск и сортировка загружают только метаданные релизов одного приложения, затем выполняют пагинацию; это O(N) по числу его релизов и подходит текущему масштабу.

Нормализованные платформы определены в `domain/artifact.rs::TARGETS`; UI получает список из API. Для общего пакета macOS под Intel и Apple Silicon используйте `darwin-universal` (macOS Universal). Формат определяется сервером по расширению в lowercase, включая tar.gz/tar.xz/tar.bz2/tar.zst. Остальные расширения тоже поддерживаются как проверенный токен длиной 1–32 ASCII-символа (`a-z`, цифры, `.`, `_`, `-`). Для файла без расширения нужен явный file_type. Если есть и расширение, и явный формат, они должны совпасть. MIME клиента не считается источником формата. Это метаданные, а не проверка содержимого или безопасности исполняемого файла. Уникальна комбинация `(release_id,target,file_type,distribution_role)`; для updater дополнительно уникальны `(release_id,target)` независимо от формата.

## Административный API

Все пути начинаются с `/api/v1/admin`. Все запросы требуют session cookie; GET/HEAD доступны admin/operator. POST/PATCH/DELETE требуют admin, точный Origin, `X-Veruna-Request: 1`, `X-CSRF-Token`. Сервис повторно проверяет действующую сессию и роль под `BEGIN IMMEDIATE` для каждого изменения, включая завершение долгой загрузки. SQL остаётся в конкретных репозиториях.

Базовый путь релизов: `/applications/{applicationId}/releases`.

| Метод / суффикс | Результат |
| --- | --- |
| GET базовый путь | `{items,total,page,per_page}` |
| POST базовый путь | 201 Release DTO |
| GET `/{releaseId}` | Release DTO |
| PATCH `/{releaseId}` | обновлённый Release DTO |
| DELETE `/{releaseId}` | 204 |
| GET `/{releaseId}/artifacts` | массив Artifact DTO |
| POST `/{releaseId}/artifacts` | multipart, 201 Artifact DTO |
| GET `/{releaseId}/artifacts/{artifactId}/download` | поток, attachment, application/octet-stream |
| DELETE `/{releaseId}/artifacts/{artifactId}` | 204 |
| POST `/{releaseId}/artifacts/{artifactId}/verify` | `{valid: true или false}` |
| GET `/artifact-options` (относительно admin) | `{targets,file_types,max_file_bytes,upload_idle_seconds}` |

Список: page ≥ 1, per_page 1–100 (по умолчанию 20), search до 200 символов — буквальная регистрозависимая подстрока версии, sort = version/created_at/updated_at, order = asc/desc. Необязательный status=draft|published фильтрует состояние. По умолчанию SemVer по убыванию. Параметры поиска/пагинации панели сохраняются в URL.

POST JSON: `{"version":"1.2.0","title":"Название","release_notes":"Изменения"}`. Обязательна только version. Название до 120 символов; пустое/null означает отсутствие названия. Описание до 20 000 символов, по умолчанию пустое. PATCH принимает непустое подмножество этих полей; title=null очищает название, null для version/release_notes запрещён. Неизвестные поля отвергаются. JSON ограничен 128 KiB.

Release DTO: id, application_id, version, title, release_notes, status, revision, created_at, updated_at, published_at, artifact_count, total_size_bytes. Artifact DTO: id, release_id, filename, target, file_type, size_bytes, sha256, created_at, distribution_role, signature_present. Даты — Unix seconds UTC. Storage key и физические пути не раскрываются.

Multipart содержит **target**, необязательные **file_type** и **distribution_role** (`installer` по умолчанию, `updater`) до ровно одного **file** с filename. Дополнительный файловый part **signature** с именем `.sig` (до 16384 байт) разрешён до или после file. Для published updater он обязателен в этом же запросе; подпись installer запрещена. Неизвестные/повторные поля и метаданные после file запрещены. Пример с уже полученными cookie и CSRF:

```sh
curl --fail-with-body -b cookies.txt \
  -H 'Origin: https://apps.veruna.systems' \
  -H 'X-Veruna-Request: 1' -H "X-CSRF-Token: $CSRF_TOKEN" \
  -F 'target=windows-x86_64' -F 'distribution_role=installer' -F 'file=@installer.exe' \
  "https://apps.veruna.systems/api/v1/admin/applications/$APPLICATION_ID/releases/$RELEASE_ID/artifacts"
```

Для подписанного updater используйте в том же запросе `-F 'distribution_role=updater' -F 'file=@updater.exe' -F 'signature=@updater.exe.sig'` после target. Криптографическую проверку выполняет клиент; сервер проверяет структуру существующим валидатором.

Исходное имя сохраняется для показа и Content-Disposition с UTF-8 filename*. Имена с `/`, `\`, `:`, управляющими символами, пустые и длиннее 255 UTF-8 байт отвергаются. Физическое имя никогда не строится из filename. Все вложенные операции проверяют связь приложения, релиза и артефакта; подмена идентификаторов даёт 404. Повторное удаление возвращает 404, сохраняя идемпотентный результат отсутствия ресурса. PATCH с прежними значениями безопасен.

Ошибки в общем envelope `{"error":{"code":"…","message":"…"}}`: 401 unauthorized, 403 forbidden, 404 not_found, 409 release_version_exists/artifact_exists/release_locked, 413 payload_too_large, 422 invalid_release/invalid_artifact/invalid_updater/updater_signature_required, 408 upload_timeout, 507 storage_full, 503 storage_busy/storage_unavailable, 500 internal_error. Внутренние пути, тела multipart, cookie и файловые системные ошибки в публичный ответ не попадают. Обрыв после успешного commit может оставить клиент без ответа: перед повтором обновите список. Проверка SHA-256 возвращает false при несовпадении содержимого; отсутствующий файл или неверный размер требуют обслуживания и дают 503.

## Физическое хранение и потоковая обработка

```text
storage.directory/
  <32 hex UUID>.blob        постоянные объекты без исходных имён
  .tmp/
    <32 hex UUID>.tmp       незавершённые записи (по умолчанию)
```

`storage.directory` — управляемый сервисом непубличный каталог. `storage.temporary_directory` по умолчанию вычисляется как `<directory>/.tmp`; его можно задать отдельно **на той же файловой системе**. Startup проверяет возможность hard link. Отдельные временный и постоянный диски не поддерживаются: они нарушили бы атомарное установление имени без дополнительного копирования. Каталог иконок не может пересекаться с постоянным или временным хранилищем. Временный каталог не может содержать постоянный.

Доступ идёт только через `ArtifactStorage` и capability-scoped `cap-std::Dir`. Ключи генерирует сервер; чтение/удаление проверяют их формат, чтение запрещает symlink и специальные файлы. Владелец каталогов — отдельный пользователь сервиса, доступ на запись другим пользователям не предоставляется (рекомендуемые права каталогов 0700, umask 0077). Файлы не имеют executable-битов, HTTP всегда отдаёт attachment/octet-stream с nosniff. Не настраивайте alias/static location на каталог хранения.

Axum Multipart читает файл порциями. Адаптер ограничивает read-ahead парсера 64 KiB, выдаёт ему отдельный бюджет 16 KiB на preamble/заголовки, текстовые поля ограничены 128 байтами. Запись через Tokio идёт порциями до 64 KiB, одновременно считается SHA-256 и фактический размер; весь файл не читается ни в RAM Rust, ни в JavaScript. Четыре общих permits ограничивают параллельные загрузки и проверки хеша, при занятости ответ 503. Долгая передача не держит транзакцию SQLite. Таймаут бездействия применяется к ожиданию следующей порции данных; общий предел продолжительности загрузки не задан. Скачивание — ReaderStream, без Range и публичных ссылок.

Upload: проверка сессии, принадлежности, draft и метаданных → create_new временного файла → потоковая запись/хеш/лимиты → flush/sync_all → атомарный **hard link без перезаписи** в постоянный каталог → unlink временного имени → sync обоих каталогов → короткая DB-транзакция с повторной проверкой прав, принадлежности/draft и уникальности → INSERT/touch → commit. Link+unlink выбран вместо обычного rename, поскольку rename может перезаписать существующий объект; сбой между link и unlink безопасно оставляет два имени одного файла.

### Синхронизация каталогов на Linux

`cap-std 3.4.6` открывает `Dir::open_ambient_dir` на Linux с `O_PATH`. Такой дескриптор позволяет выполнять операции относительно каталога, но непригоден для `fsync`: `into_std_file()` только передаёт дескриптор, а `try_clone()` дублирует его с тем же `O_PATH`. Это было причиной `Bad file descriptor (os error 9)` при запуске: `initialize()` создавал хранилище, открывал SQLite и применял миграции, затем останавливался на первом `sync_all()` в `LocalArtifactStorage::reconcile()`, ещё до инициализации иконок. SQLite не был источником этой ошибки. Такой же дефект находился в `LocalArtifactStorage::promote()`, `LocalArtifactStorage::remove()` и `IconStorage::store()`.

Минимальное воспроизведение без SQLite и HTTP:

```rust
let root = cap_std::fs::Dir::open_ambient_dir(path, cap_std::ambient_authority())?;
root.try_clone()?.into_std_file().sync_all()?; // Linux: EBADF
```

Нативная Linux-трассировка через `strace -yy -e trace=openat,openat2,fsync` подтвердила причину и исправление (номера дескрипторов сокращены):

```text
openat(..., directory, O_RDONLY|O_CLOEXEC|O_PATH|O_DIRECTORY) = fd
fsync(duplicated_fd) = -1 EBADF (Bad file descriptor)
openat2(fd, ".", {flags=O_RDONLY|O_LARGEFILE|O_CLOEXEC,
                  resolve=RESOLVE_NO_MAGICLINKS|RESOLVE_BENEATH}, 24) = readable_fd
fsync(readable_fd) = 0
```

Общий внутренний `infrastructure::directory::sync_directory()` на Linux открывает `"."` для чтения через уже удерживаемый capability `Dir` и вызывает `sync_all()` нового дескриптора. Внешний путь не разрешается повторно: синхронизируется тот же каталог даже после переименования. На остальных ОС сохранён прежний механизм. Ошибки открытия и синхронизации передаются вызывающему коду; пропуска `fsync` или подавления ошибок нет. Все существовавшие места синхронизации каталогов артефактов и иконок используют эту функцию; синхронизация содержимого файлов, порядок hard link/unlink до commit БД, проверка ключей, symlink и размеров не изменены. Компенсационная очистка по-прежнему допускает остатки до следующего startup.

Регрессия `cargo test --locked --test storage` проверяет инициализацию, первую синхронизацию пустого хранилища, сохранение, повторное открытие, очистку следов прерванной загрузки, проверку SHA-256, чтение и удаление с вложенным и отдельным временным каталогом. На Linux до исправления тест падает при первом `reconcile()`. Дополнительный Linux unit-тест проверяет синхронизацию после переименования каталога и замены исходного пути обычным файлом.

### Ошибки и восстановление

- Ошибка/отмена во время передачи удаляет временный файл через guard; если процесс завершился раньше очистки, файл удаляется на следующем startup.
- Ошибка до попытки commit компенсирует также установленный постоянный файл. Параллельные загрузки одинаковой комбинации target/file_type/role (либо второго updater для target) разрешает UNIQUE: проигравшая получает 409 и освобождает свой объект.
- Перед await commit постоянный файл сохраняется даже при ошибке/отмене: commit мог уже произойти. Нельзя удалять файл при неоднозначном результате. Непривязанный объект позже убирает startup.
- Удаление: сначала подтверждённый commit удаления строк, потом unlink файлов. Ошибка unlink не восстанавливает уже удалённые строки; сервер пишет предупреждение и оставляет безопасный непубличный остаток для startup cleanup. Открытый файловый дескриптор позволяет уже начавшемуся скачиванию завершиться; гонка до открытия файла может вернуть 503.
- Нехватка места даёт 507, если ОС сообщает StorageFull; прочие ошибки записи — безопасный 500. Частичный файл не получает DB-ссылку и не скачивается. Освободите место, перезапустите для очистки остатков и повторите загрузку.

**Обслуживание выполняется одним экземпляром сервера на startup до listener.** Сначала проверяются все DB-ссылки: корректный ключ, обычный файл, ожидаемый размер. Отсутствующий/укороченный файл останавливает запуск без удаления записей; восстановите согласованную копию данных. Затем удаляются только серверные UUID.tmp и непривязанные UUID.blob. Произвольные прочие файлы не трогаются. Полный SHA-256 на startup не пересчитывается; проверяйте его по запросу администратора. Сложного фонового очистителя нет; остатки неоднозначных commit/удалений могут занимать место до перезапуска. Не запускайте два экземпляра и не запускайте обслуживание параллельно с работающим сервером.

## Конфигурация и proxy

По умолчанию max_file_bytes = 2147483648 (2 GiB), max_request_bytes = 2148532224 (файл + 1 MiB multipart overhead), upload_idle_seconds = 120 (допустимо 1–86400). Размеры — положительные целые, max_request_bytes строго больше max_file_bytes; размер файла должен помещаться в положительный INTEGER SQLite. Настройки доступны через TOML и соответствующие `STORAGE__…`.

Пример production:

```toml
[storage]
directory = "/var/lib/veruna-releases/storage"
icons_directory = "/var/lib/veruna-releases/icons"
# По умолчанию /var/lib/veruna-releases/storage/.tmp
# temporary_directory = "/var/lib/veruna-releases/upload-tmp"
max_file_bytes = 2147483648
max_request_bytes = 2148532224
upload_idle_seconds = 120
```

Nginx в HTTPS server (все остальные настройки TLS/auth origin остаются прежними):

```nginx
location /api/v1/admin/applications/ {
    client_max_body_size 2049m;
    client_body_timeout 120s;
    proxy_request_buffering off;
    proxy_http_version 1.1;
    proxy_read_timeout 300s;
    proxy_send_timeout 120s;
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Forwarded "";
}
```

Увеличивая размер в приложении, согласуйте client_max_body_size и запас multipart overhead. `proxy_request_buffering off` передаёт поток Rust сразу; иначе proxy может сначала записать всю загрузку на собственный временный диск. Учитывайте ограничения внешнего балансировщика и свободное место обоих компонентов. Прокси может вернуть собственный HTML 413/таймаут до Axum; UI покажет ошибку запроса. Не переписывайте Origin. Для длительной проверки хеша увеличьте proxy_read_timeout; UI не ограничивает её 15 секундами обычных JSON-запросов.

## Резервное копирование, перенос и обновление

Простой согласованный вариант для одного сервера:

1. Остановите сервер и дождитесь завершения запросов. Не копируйте меняющиеся SQLite и файлы независимо.
2. Сохраните SQLite вместе с существующими `-wal`/`-shm` и оба каталога постоянных данных: дистрибутивы и иконки. Альтернатива после остановки — SQLite backup API для единого снимка БД. Конфигурацию сохраняйте отдельно. Временные загрузки можно не включать.
3. Для восстановления при остановленном сервере восстановите **один согласованный набор**, владельца/права и настройки путей. Не накладывайте копию БД на текущие WAL-файлы другой копии.
4. Запустите сервер: миграции, проверка ссылок/размеров и cleanup выполнятся до открытия порта. Проверьте вход, скачивание и SHA-256 нужных объектов.

Внутренние ключи относительны. Для переноса на другой локальный диск остановите сервер, скопируйте постоянный каталог целиком, измените storage.directory и при необходимости temporary_directory; записи БД менять не нужно. Если временный каталог задан отдельно, перенесите его на тот же новый filesystem или вернитесь к `.tmp` по умолчанию. Бинарник обновляется независимо: заменяется только executable, данные остаются снаружи. `data/`, SQLite, frontend/dist, node_modules и target исключены из Git; пользовательские production-пути размещайте вне checkout. Только UI и миграции встраиваются в бинарник, дистрибутивы — никогда.
