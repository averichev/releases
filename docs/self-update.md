# Обновление Veruna Releases

Администратор управляет установленным сервисом на странице **Обновление сервиса** (`/admin/self-update`). Первую сборку с поддержкой обновлений установите обычным способом. Для дальнейших проверок задайте источник в локальной конфигурации.

## Источник и режим

Для проверки достаточно одной строки в секции `[self_update]` файла `veruna.toml`. Укажите полный URL манифеста продукта на сервере издателя.

```toml
[self_update]
manifest_url = "https://updates.example.org/releases/manifest.json"
```

Адрес также можно задать через `SELF_UPDATE__MANIFEST_URL`. Клиент получает один манифест на проверку, ищет стабильный подписанный `executable` для своей платформы и проверяет его JWS встроенным публичным ключом. Файл может загружаться с того же origin, включая порт. Предел одного файла — 256 МиБ. Разрешён HTTPS и HTTP по числовому loopback-адресу для локального стенда.

Для установки на Linux добавьте в ту же секцию `mode = "supervisor"` или `mode = "standalone"` и `directory = "/var/lib/veruna-releases/updates"`.

| Режим | Поведение |
| --- | --- |
| `external` (по умолчанию при заданном источнике) | macOS, Windows и Linux проверяют подписанный выпуск. Бинарник устанавливает оператор или пакетный менеджер. Каталог обновлений не требуется. |
| `supervisor` | На Linux исходный процесс сохраняет PID и запускает сервер из приватной рабочей копии. Подходит для службы и бинарника, принадлежащего root. |
| `standalone` | На Linux передаёт управление временной копии, заменяет исходный файл и запускает новую версию с новым PID. Бинарник и его каталог должны принадлежать пользователю сервиса, staging должен находиться на той же файловой системе. |

Для установки нужен отдельный каталог на исполняемой локальной файловой системе. Владелец — UID сервиса, права — `0700`. Используйте пути без симлинков. Разместите SQLite, иконки, дистрибутивы и доверенную конфигурацию отдельно от этого каталога. Укажите фиксированный ненулевой порт на loopback или wildcard. При включённой установке сервер использует именно этот порт и завершает запуск при конфликте. Относительные пути разрешаются от рабочего каталога процесса.

## Идентичность издателя

Постоянный UUID v4 Veruna Releases — `791882f1-c3a0-4251-abd2-e6e40fd7f5df`. UUID и публичный Ed25519 JWK хранятся вместе и встраиваются при сборке. Один раз укажите `product_id` и `public_key.x` из этого файла в карточке продукта на сервере публикации, в разделе **Настройки → Подписанные обновления**. [Публичная идентичность Veruna Releases](../deploy/self-update-identity.json)

Закрытый ключ издателя хранится отдельно от репозитория и дистрибутивов. На машине подписания его штатный путь — `~/.config/veruna-releases/update-signing.pem`. Сохраните резервную копию в защищённом хранилище издателя. Для сборки на другой машине передайте путь к тому же ключу через `RELEASE_SIGNING_KEY`.

## Публикация и установка

1. Соберите выпуск через `make release`. При наличии ключа издателя команда создаёт и проверяет отдельную Ed25519-подпись `.jws` для каждого готового бинарника. Явно заданный отсутствующий или неподходящий ключ останавливает сборку. На Linux `./veruna-releases --standalone-updater-build-info` выводит версию, UUID, полный Rust target и отпечаток данных.
2. Загрузите бинарник и соседний `.jws` как **Пакет обновления** и опубликуйте стабильную версию. В `/{slug}/manifest.json` появится `signed_metadata` для файла с назначением `executable`. Для каждого target выпускайте один ABI. [Публикация из CLI](cli-publication.md)

3. Откройте **Обновление сервиса → Проверить обновления**. На Linux нажмите **Подготовить** для выбранной версии. Подготовка сверяет подпись и хеш файла, запускает проверку совместимости и сохраняет резервную копию. Сервис продолжает работу. Подготовку можно отменить.
4. Нажмите **Установить и перезапустить** и подтвердите версию. После восстановления соединения страница покажет итог. При успешном переходе нажмите **Обновить страницу**, чтобы загрузить новый встроенный интерфейс.

## Совместимость данных и восстановление

Автоматическая установка требует точного совпадения Rust target и отпечатка встроенных миграций SQLx и формата файлов. При несовместимом изменении записываемых данных вне миграций разработчик повышает метку формата в `infrastructure/database.rs`. Версии с новым отпечатком устанавливайте вручную после остановки сервиса и согласованного резервного копирования SQLite, иконок и дистрибутивов. [Резервное копирование](releases.md#резервное-копирование-перенос-и-обновление).

При сбое запуска или проверки готовности обновлятор пытается вернуть предыдущий бинарник. SQLite и пользовательские файлы продолжают использоваться по прежним путям. Если панель сообщает о необходимости восстановления, остановите службу и оставшиеся процессы обновления, затем запустите исходный бинарник с `--standalone-updater-recover` под тем же пользователем, из прежнего рабочего каталога и с прежней конфигурацией. Запустите службу штатным способом и проверьте версию и результат операции.

## HTTP

Все операции требуют действующую admin-сессию. Для POST обязательны Origin, `X-Veruna-Request: 1` и CSRF-токен. Пути относительны к `/api/v1/admin/self-update`.

| Запрос | Ответ или тело запроса |
| --- | --- |
| GET | Текущая версия, target, режим, возможность установки и статус. При отключённом источнике `mode` и `status` равны `null`. |
| POST `/check` | HTTP 202 и идентификатор операции в `operation_id`. |
| POST `/prepare` | `{"check_id":"…","version":"1.2.3"}` из результата проверки. |
| POST `/install`, POST `/cancel` | `{"operation_id":"…"}` подготовленного выпуска. |

Принятую операцию отслеживайте через GET по её идентификатору. При HTTP 409 перечитайте состояние. Прямой loopback-маршрут `/api/v1/health/self-update` обслуживает проверку нового процесса в Linux-режимах установки.

## Сквозная проверка

Проверка использует две версии Linux-бинарника и одноразовую тестовую пару ключей. На Linux сначала соберите фронтенд. Для примера нужны Rust, Python 3.11+, curl, C-компилятор и OpenSSL с Ed25519.

```sh
test_dir=$(mktemp -d)
python3 scripts/smoke_self_update.py init "$test_dir/issuer"
export RELEASE_UPDATE_IDENTITY="$test_dir/issuer/identity.json"
for version in 1.0.0 1.1.0; do
  RELEASE_VERSION="$version" cargo build --locked --target-dir target
  cp target/debug/veruna-releases "$test_dir/$version"
done
unset RELEASE_UPDATE_IDENTITY
for mode in supervisor standalone; do
  python3 scripts/smoke_self_update.py run "$test_dir/issuer" "$test_dir/1.0.0" "$test_dir/1.1.0" --mode "$mode"
done
```

Скрипт публикует подписанный файл через API временного сервера. Клиент находит его по единственному URL манифеста. Проверяются установка, отмена подготовки, отказ при несовместимости данных и откат после сбоя запуска.
